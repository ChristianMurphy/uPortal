# Platform Alternatives for uPortal 6.0 (Java 25 / Spring Framework 7 / Hibernate 7 / Jakarta EE 11): keep, upgrade or replace each legacy platform choice

Notes are as of 2026-10-10. Many primary doc hosts (docs.spring.io, tomcat.apache.org, jetty.org, docs.hibernate.org, lucene.apache.org, infinispan.org, docs.liquibase.com, webtide.com) could not be fetched from this environment because of DNS failures. For those, I used the same docs' source files on GitHub (raw.githubusercontent.com / github.com), which are primary sources, or search-engine snippets of the official pages. Search-snippet-only facts are marked "(search snippet)". GitHub release pages show only day and month, so the years given for those entries are inferred and marked as such.

## 1. Servlet runtime / packaging: external Tomcat 11 vs Spring Boot 4 vs Jetty 12.x (multi-environment, cross-context) vs others

### Takeaway
External Tomcat 11 is still the lowest-risk runtime for a portal that hosts several webapps with cross-context dispatch. It implements Servlet 6.1 / Jakarta EE 11, has no announced EOL, still supports `crossContext`, and is the Tomcat version that both Spring Boot 4 and CAS 8 build on. Its `legacyAppBase` feature can auto-convert `javax` WARs on deploy. Spring Boot 4 can be adopted incrementally inside the existing WAR (SpringBootServletInitializer + @ImportResource + Boot BOM/Actuator), but Spring Boot does not document hosting additional WAR contexts in embedded Tomcat, so it is not a replacement for the multi-webapp container. Jetty 12.0.8+ / 12.1.x does let ee8 (javax) and ee10/ee11 (jakarta) webapps run side by side with cross-environment cross-context dispatch, and Jetty's own test suite covers that. However, the feature is young: an ee10/ee11 bug where the dispatched servlet ran with the *source* context's identity and classloader was only fixed on 30 Sep 2026. Pluto also shares container objects across the boundary, so "unmodified javax portlet WARs next to a Jakarta uPortal" would still need a bridging layer. Treat it as a prototype option, not the default path.

### Cited Findings

**Tomcat 11 status and support**
- Tomcat 11.0 supports Jakarta Servlet 6.1, Pages 4.0, EL 6.0, WebSocket 2.2, Authentication 3.1 and Annotations 3.0, and requires Java 17 or later. — [Tomcat 11 migration guide](https://tomcat.apache.org/migration-11.0.html) (search snippet)
- The official "which version" page lists 11.0.x as supported (Java 17+). The search snapshot showed latest 11.0.18, which is stale: CAS 8.0.x pins Tomcat 11.0.26. — [Tomcat whichversion](https://tomcat.apache.org/whichversion) (search snippet); [apereo/cas 8.0.x libs.versions.toml](https://raw.githubusercontent.com/apereo/cas/8.0.x/gradle/libs.versions.toml)
- Tomcat 9.0.x support ends "no earlier than March 31, 2027", and a 9.1.x branch is planned to continue after that. No EOL date has been announced for 10.1 or 11; third-party estimates (OpenLogic) of ~2030 for 10.x and ~2034 for 11 are guesses, not official. — [Tomcat whichversion](https://tomcat.apache.org/whichversion) (search snippet); [OpenLogic Tomcat 9 EOL](https://www.openlogic.com/blog/prepare-for-tomcat-9-eol); [endoflife.ai Tomcat](https://endoflife.ai/tomcat)
- No Tomcat 12 development line turned up in searches.
- `crossContext` is still a Context attribute in Tomcat 11: "Set to true if you want calls within this application to ServletContext.getContext() to successfully return a request dispatcher for other web applications running on this virtual host. Set to false (the default) in security conscious environments…" — [Tomcat 11.0.x config/context.xml source](https://raw.githubusercontent.com/apache/tomcat/11.0.x/webapps/docs/config/context.xml)
- Tomcat 11 `Host` has a `legacyAppBase` (default `webapps-javaee`). "Java EE applications packaged as WAR files or directories placed in this directory will be converted to Jakarta EE using the Apache Tomcat Migration Tool for Jakarta EE… The resulting WAR or directory will be placed in the appBase." Non-default options require running `$CATALINA_HOME/bin/migrate.sh` manually. — [Tomcat 11.0.x config/host.xml source](https://raw.githubusercontent.com/apache/tomcat/11.0.x/webapps/docs/config/host.xml)
- The migration tool renames only Java EE packages ("not all javax.* packages are part of Java EE"), so `javax.portlet` would *not* be renamed. It converts "package references in classes, String constants, configuration files, JSPs, TLDs etc." and removes JAR signatures. — [apache/tomcat-jakartaee-migration README](https://github.com/apache/tomcat-jakartaee-migration)

**Spring Boot 4.x on top of an XML-configured WAR**
- Spring Boot 4.0 depends on Jakarta Servlet 6.1, Tomcat 11.0, Jetty 12.1, Hibernate 7.2 (Validator 9.0, Persistence 3.2) and Jackson 3.0. Jackson 2 support "ships in a deprecated form." — [Spring Boot 4.0 Release Notes (wiki)](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Release-Notes)
- Boot 4 drops Undertow because Undertow is not yet Servlet 6.1 compatible. "We do not recommend deploying Spring Boot 4.0 applications to a non-Servlet 6.1 compliant container." For deploying a war to an external container, "you need to switch the dependency `spring-boot-starter-tomcat` to `spring-boot-starter-tomcat-runtime`." — [Spring Boot 4.0 Migration Guide](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide)
- Boot 4 is modularized: it "now ships smaller focused modules rather than several large jars", and each module's root package is `org.springframework.boot.<technology>`. "Classic starters" give back a full classpath for incremental migration, but "we recommend that you eventually migrate your application away from using the classic starters." Upgrade to the latest 3.5.x first. — [Spring Boot 4.0 Migration Guide](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide)
- Deployable war steps: subclass `SpringBootServletInitializer` and override `configure`, use war packaging, and move the embedded container to `providedRuntime` in Gradle ("`providedRuntime` is preferred to Gradle's `compileOnly`"). For an existing app, an XML-defined context "can be added through an `@ImportResource` annotation". web.xml servlets and filters become `ServletRegistrationBean` / `FilterRegistrationBean` beans. "War deployment is not supported for WebFlux applications." — [Spring Boot docs source: traditional-deployment.adoc](https://raw.githubusercontent.com/spring-projects/spring-boot/main/documentation/spring-boot-docs/src/docs/antora/modules/how-to/pages/deployment/traditional-deployment.adoc)
- JSP limitations (current reference): "With Jetty and Tomcat, it should work if you use war packaging. An executable war will work when launched with `java -jar`, and will also be deployable to any standard container. JSPs are not supported when using an executable jar. Creating a custom `error.jsp` page does not override the default view for error handling." Embedded servlet support covers only Tomcat and Jetty. — [Spring Boot docs source: web/servlet.adoc](https://raw.githubusercontent.com/spring-projects/spring-boot/main/documentation/spring-boot-docs/src/docs/antora/modules/reference/pages/web/servlet.adoc)
- Embedded container customization goes through `WebServerFactoryCustomizer` and `TomcatServletWebServerFactory`, which has context customizers. Boot 4 still has the protected hook `TomcatServletWebServerFactory.getTomcatWebServer(Tomcat tomcat)`, now in module `spring-boot-tomcat`, package `org.springframework.boot.tomcat.servlet`. — [web/servlet.adoc](https://raw.githubusercontent.com/spring-projects/spring-boot/main/documentation/spring-boot-docs/src/docs/antora/modules/reference/pages/web/servlet.adoc); [GitHub code: TomcatServletWebServerFactory.java](https://github.com/spring-projects/spring-boot/blob/main/module/spring-boot-tomcat/src/main/java/org/springframework/boot/tomcat/servlet/TomcatServletWebServerFactory.java)
- Adding a second WAR to embedded Tomcat is only community-documented: subclass the factory, override the server-creation hook and call `tomcat.addWebapp(...)`. Inside a fat jar the extra webapp needs an explicit parent class loader. The answer found targets the old Boot 1.x API. — [community answer (Tencent Cloud)](https://cloud.tencent.com/developer/ask/224891); no Spring-documented support found.
- As of the search date, Spring Boot 4.1.x is the stable line (4.1.1 named as latest stable) and 4.2 is in development. — [Spring Boot 4.2 traditional deployment page](https://docs.spring.io/spring-boot/4.2/how-to/deployment/traditional-deployment.html) (search snippet)
- Precedent: Apereo CAS 8.0.x (a large Spring app with a long XML/WAR history) builds on Spring Boot 4.1.0, Spring Framework 7.0.8, Tomcat 11.0.26, Jetty 12.1.11, Hibernate 7.4.5.Final, Spring Security 7.1.0 and Spring Web Flow 4.0.1, with Java 25 source/target. — [apereo/cas 8.0.x libs.versions.toml](https://raw.githubusercontent.com/apereo/cas/8.0.x/gradle/libs.versions.toml); [apereo/cas 8.0.x gradle.properties](https://raw.githubusercontent.com/apereo/cas/8.0.x/gradle.properties)
- CAS overlays historically let the embedded app server be chosen (tomcat/jetty/undertow) or left empty "to deploy CAS to an external application server" (older overlay README). A CAS operator runbook excludes `org.apache.tomcat.embed` and deploys the war to a standalone Tomcat. — [gitee CAS overlay mirror](https://gitee.com/cuihui2012/cas-overlay-template); [Cloudogu "Upgrading CAS"](https://docs.cloudogu.com/en/docs/dogus/cas/development/Upgrading_CAS/)

**Jetty 12.x multi-environment and cross-context dispatch**
- Jetty 12 environments: ee8 = Servlet 4 / `javax.servlet`, ee9 = Servlet 5 / `jakarta`, ee10 = Servlet 6 / `jakarta`. Jetty 12.1.0 added a "New Jakarta EE11 Server Environment" and per-environment configuration for "ee8, ee9, ee10, ee11". — [Jetty 12.1.0 release discussion #13474](https://github.com/jetty/jetty.project/discussions/13474); [Jetty deploy docs](https://jetty.org/docs/jetty/12/operations-guide/deploy/index.html) (search snippet)
- The official download page lists Jetty 12.1 as Stable/Supported with EE8 through EE11 support and minimum JVM 17. Jetty 10/11 community support ended 1 Jan 2024 and official EOL was 1 Jan 2025. — [Jetty downloads](https://jetty.org/download.html) (search snippet); [jetty.project issue #10485](https://github.com/jetty/jetty.project/issues/10485)
- Cross-context dispatch was removed in early Jetty 12 and reintroduced by PR #11451 "Reintroduce Cross Context Dispatch in Jetty 12" (merged 25 Mar 2024), shipped in Jetty 12.0.8 (released 3 Apr; year inferred as 2024). — [Jetty 12.0.8 release](https://github.com/jetty/jetty.project/releases/tag/jetty-12.0.8); [PR #11451](https://github.com/jetty/jetty.project/pull/11451)
- Webtide (Jetty maintainers): "a web application based on the javax namespace (EE8) can now dispatch requests to, or include responses from, a web application based on the jakarta namespace (EE9 or EE10)". They brought it back because commercial clients still use it in legacy applications. — [Webtide blog "Back to the Future with Cross-Context Dispatch"](https://webtide.com/back-to-the-future-with-cross-context-dispatch/) (search snippet)
- It is opt-in per context: `<Set name="crossContextDispatchSupported">true</Set>` on each `WebAppContext` (ee8, ee9, ee10, ee11), or `ServletContextHandler.setCrossContextDispatchSupported(true)`. Default is `false` in core `ContextHandler`. — [GitHub code search: ccd-ee8.xml / ccd-ee10.xml / ccd-ee11.xml test configs, ContextHandler.java](https://github.com/jetty/jetty.project/tree/jetty-12.1.x/tests/test-cross-context-dispatch)
- Jetty's cross-context test plans explicitly cover the reverse (jakarta→javax) direction that uPortal needs. Examples: `ee10-forward-to-ee8-include-ee9-dump.txt`, `ee11-forward-to-ee8-include-ee9-dump.txt`, `ee10-session-ee8-ee9-ee8.txt`, `ee11-session-ee8-ee9-ee8.txt`, `ee11-session-forward-to-ee8-session-include-ee9-dump.txt`. — [jetty.project tests/test-cross-context-dispatch/ccd-tests/src/test/resources/plans](https://github.com/jetty/jetty.project/tree/jetty-12.1.x/tests/test-cross-context-dispatch/ccd-tests/src/test/resources/plans)
- Limitations from the maintainer review of PR #11451: multipart parameters are "a bit limited" and "can't do cross environment dispatch". Cross-context dispatch "bypasses security handler". Cross-context sessions work via "cross context cookies and shared session id manager". — [PR #11451](https://github.com/jetty/jetty.project/pull/11451)
- Follow-up bugs: "Cross context dispatch to root context uses incorrect target path" (#12683), "Cross Context Dispatch with Async does not honor context" (#13144), "Port async cross context dispatch to ee11" (#13214). — [Jetty 12.1.0 discussion](https://github.com/jetty/jetty.project/discussions/13474)
- Recent correctness fix (important for Pluto): in ee10 and ee11, a servlet reached through a cross-context `RequestDispatcher` used to run with the *source* context's identity. `getServletContext()` returned the source context. PR #15763 makes it use the target's `getServletContext`/`getContextPath`, run in the target's scope (ClassLoader, current context, scope listeners) and "matches ee9 behaviour". It was merged to `jetty-12.1.x` on 30 Sep 2026; the project board suggests 12.1.14, not yet confirmed. — [PR #15763](https://github.com/jetty/jetty.project/pull/15763)
- Conflicting signal: the ee8 `ContextHandler` javadoc says the cross-context support flag "Will be removed from ee10 onwards". The current ee10/ee11 sources, however, still expose `setCrossContextDispatchSupported`. — [Jetty ee8 ContextHandler javadoc](https://javadoc.jetty.org/jetty-12/org/eclipse/jetty/ee8/nested/ContextHandler.html) (search snippet) vs [GitHub code search results in ee10/ee11 Dispatcher.java](https://github.com/jetty/jetty.project/blob/jetty-12.1.x/jetty-ee11/jetty-ee11-servlet/src/main/java/org/eclipse/jetty/ee11/servlet/Dispatcher.java)

**Other containers**
- Undertow is not Servlet 6.1 compatible; Spring Boot tracks this in issue #46917, and a 2.4.0.Alpha1 targeting EE 11 has been mentioned without a timeline. — [Spring Boot 4.0 Migration Guide](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide); [besthub.dev article](https://www.besthub.dev/articles/why-spring-boot-4-0-dropped-undertow-and-how-to-migrate-80425c839b71) (secondary)

### Inferences
- **Recommended default: keep the external Tomcat 11 deployment model** (shared/lib + `crossContext="true"` on uPortal and portlet contexts). Spring Boot 4 and CAS 8 both build on Tomcat 11, so this is the best-trodden Jakarta EE 11 path. It also keeps uPortal-start's "drop portlet WARs into Tomcat" operating model.
- Tomcat's `legacyAppBase` auto-conversion only touches Java EE packages (`javax.servlet` → `jakarta.servlet`) and leaves `javax.portlet` alone. A javax portlet WAR would therefore come out with `jakarta.servlet` + `javax.portlet` references, which works only if the shared Portlet API / Pluto container jars in shared/lib use that same mixed namespace. That ties the shared/lib API choice to the conversion approach (see the companion note portlets_on_jakarta.md).
- **Spring Boot adoption, staged:** (1) import `spring-boot-dependencies` as a Gradle `platform()` purely for version alignment. (2) Add `SpringBootServletInitializer` with `@ImportResource` for the 113 XML contexts and keep war packaging and an external Tomcat via `spring-boot-starter-tomcat-runtime`. (3) Add Actuator. JSPs keep working only with war packaging. Do not plan an executable-jar uPortal while JSPs and XSLT-in-webapp resources remain, and do not plan on embedded Tomcat hosting the portlet WARs: that path needs undocumented `Tomcat.addWebapp` overrides, careful parent-classloader wiring for shared Pluto/Portlet API jars, and `crossContext` via a context customizer. None of it is a supported Spring Boot feature.
- **Jetty 12.1 as a "run legacy javax portlet WARs unmodified" bridge:** servlet-level forward/include from ee11 → ee8 is tested by Jetty. Pluto's dispatch, though, does more than include a servlet. uPortal stores container objects (portlet request/response contexts, Pluto container services) in request attributes, and the portlet WAR's `PortletServlet` casts them to Pluto/Portlet API interfaces loaded from a shared classloader. If uPortal compiles those objects against `jakarta.servlet` and the ee8 webapp sees `javax.servlet`-based interfaces, the casts fail unless a javax↔jakarta adapter layer is written. Combined with the very recent classloader/context fix (#15763), the security-handler bypass and the multipart limits, this is a research spike (worth a prototype), not a production plan for 6.0.
- Jetty would also mean replacing all uPortal-start Tomcat management tasks and Tomcat-specific config (server.xml, context.xml, shared/lib layout), so switching has a large operational cost on top of the technical risk.

### Gaps
- Could not fetch the full Webtide blog post (DNS failure), so I could not confirm in its exact wording that dispatch works in the jakarta→javax direction. The direction is supported by Jetty's test plan file names, not by the blog text.
- No primary source found on whether Jetty's environment classloaders can share one "shared lib" (like Tomcat shared/lib) across ee8 and ee11 webapps, or how request attributes holding container objects behave across environments.
- No official Tomcat 10.1/11 EOL date exists. Tomcat 12 status was not found.
- No primary source found for Spring Boot officially supporting multiple webapp contexts in embedded Tomcat. No precedent was found of a portlet container (Pluto or Liferay) running on Spring Boot embedded. Liferay was not researched in depth.
- Open Liberty, Payara and WildFly were not researched for multi-WAR cross-context portal hosting. No evidence was found either way.

## 2. Gradle build modernization (Kotlin DSL, version catalogs, convention plugins, Declarative Gradle)

### Takeaway
Gradle recommends Kotlin DSL for *new* builds (default since 8.2) and `build-logic` included builds with convention plugins over `buildSrc`. A version catalog (`gradle/libs.versions.toml`) is Gradle's own best practice for centralizing versions, and Renovate supports both catalogs and `gradle.properties` versions, so the switch is optional for Renovate. Groovy DSL is not deprecated, and migration can be file-by-file because the two DSLs can coexist. Declarative Gradle is still experimental. The best payoff order: convention plugins in `build-logic/` and a version catalog first, configuration-cache compatibility next, Kotlin DSL conversion last.

### Cited Findings
- "Starting with Gradle 8.2, creating new builds using gradle init defaults to generating Gradle builds using Kotlin DSL." IntelliJ IDEA 2023.1+ and Android Studio Giraffe also default to it. Groovy DSL support "will continue for existing projects or those who prefer to use it." — [Gradle blog: Kotlin DSL is now the default](https://blog.gradle.org/kotlin-dsl-is-now-the-default-for-new-gradle-builds); Google adds Groovy will keep working "with no plans for deprecation" — [Android Developers blog](https://android-developers.googleblog.com/2023/04/kotlin-dsl-is-now-default-for-new-gradle-builds.html)
- Trade-off: Kotlin script compilation is slower than Groovy DSL, but its results are stored in Gradle's local/remote caches. — [Android Developers blog](https://android-developers.googleblog.com/2023/04/kotlin-dsl-is-now-default-for-new-gradle-builds.html)
- Gradle Best Practices: "Use Kotlin DSL – Prefer the Kotlin DSL (`build.gradle.kts`) over the Groovy DSL (`build.gradle`) when authoring new builds". Reasons given are strict typing (better IDE completion and navigation), readability, and a single-language stack. — [Gradle best_practices_general.adoc](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/best-practices/best_practices_general.adoc)
- Gradle Best Practices: "Favor `build-logic` Composite Builds for Build Logic": "The preferred location for build logic is an included build… Any change in `buildSrc` causes the entire build to become out-of-date… we recommend using it over `buildSrc` in most cases". Also "Use Convention Plugins for Common Build Logic". — [Gradle best_practices_structuring_builds.adoc](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/best-practices/best_practices_structuring_builds.adoc)
- Gradle Best Practices: "Use Version Catalogs to Centralize Dependency Versions… Use a centralized `libs.versions.toml` file in your `gradle/` directory". "Avoid declaring versions in `project.ext`, constants, or local variables". Catalogs "only influence declared versions, not resolved versions", so pair them with platforms and locking. Naming rules: dashes, camelCase conversion, `-plugin` suffix. — [Gradle best_practices_dependencies.adoc](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/best-practices/best_practices_dependencies.adoc)
- Migration guidance: both DSLs can apply each other's scripts, so migration need not be all at once. Update Gradle, plugins and IDE first, and adopt the `plugins {}` block in Groovy before converting. — [Gradle "Migrating build logic from Groovy to Kotlin"](https://docs.gradle.org/current/userguide/migrating_from_groovy_to_kotlin_dsl.html) (search snippet)
- Practitioner reports: conversion is mostly mechanical (quotes, parentheses, `=` assignments, `plugins {}`), done incrementally (settings, then root, then subprojects). One multi-module report says navigating extra-property definitions "was often impossible in Groovy" and that this is fixed with Kotlin DSL. Most reports are from the Gradle 5–8 era. — [encircle360](https://encircle360.com/en/blog/gradle-kotlin-dsl-migration); [ProAndroidDev case study](https://proandroiddev.com/takeaways-from-migrating-a-complex-android-project-to-gradle-kotlin-dsl-eaeb5ccd8c84); [Notificare](https://notificare.com/blog/2023/11/10/migrating-to-kotlin-dsl-and-version-catalog)
- JetBrains IntelliJ has an IDE-assisted "Migrate Gradle build scripts to Kotlin DSL" workflow. — [JetBrains help](https://www.jetbrains.com/help/idea/migrate-gradle-build-scripts-to-kotlin-dsl.html.md) (search snippet)
- Configuration cache: GA in Gradle 8.1. In Gradle 9.0 it is "the preferred mode of execution. While not yet required, Gradle encourages adoption by prompting users and gradually phasing out incompatible APIs." Gradle 9.0 uses Kotlin 2.2 and Groovy 4.0 for build scripts. Gradle 9.2.0 shipped 29 Oct 2025, and 9.7.x exists by Oct 2026. — [Gradle 9.0.0 release notes](https://docs.gradle.org/9.0.0/release-notes.html); [Gradle 9.2.0 release notes](https://docs.gradle.org/9.2.0/release-notes.html); [Gradle 9.7.1 release notes](https://docs.gradle.org/9.7.1/release-notes.html) (search snippets)
- Declarative Gradle is "an experimental project, now in its third Early Access Preview" (EAP3, April 2025), "not ready for production use". The roadmap lists EAP4 for 2025 Q4. No 2026 status was found. — [Declarative Gradle EAP3 blog](https://blog.gradle.org/declarative-gradle-april-2025-update); [declarative.gradle.org roadmap](https://declarative.gradle.org/docs/ROADMAP/)
- Renovate can update versions defined in `gradle.properties`, in `*.versions.toml` in any directory, and in `*.toml` under `gradle/`. It does not handle catalogs with version ranges or `reject`/`rejectAll` constraints, or catalogs with custom names not ending in `.toml`. — [Renovate docs/usage/java.md (mirror)](https://git.shivering-isles.com/github-mirror/renovatebot/renovate/-/blob/8af89d27d01982dbe72297b601ad4f618f57d5eb/docs/usage/java.md)
- Gradle pitfall: `${...}` placeholders in a TOML catalog that point at `gradle.properties` values are not evaluated. — [Gradle forum](https://discuss.gradle.org/t/libs-versions-toml-doesnt-understand-gradle-properties/41406)
- Real-world precedent: Ehcache 3 itself uses a `build-logic/` included build. — [ehcache/ehcache3 repo root](https://github.com/ehcache/ehcache3)

### Inferences
- Cost estimate for ~50 build files + Groovy buildSrc plugins. Mechanical conversion of simple module scripts is cheap, probably minutes each once conventions exist. The real cost is in the buildSrc Groovy plugins (custom Tomcat/HSQLDB/CAS/portlet-deploy tasks in uPortal-start). They should be rewritten as typed Kotlin or Java convention/binary plugins in `build-logic/`, which is also when configuration-cache problems (`project` access at execution time, `ext` properties) get fixed. Move those tasks first; script syntax second.
- Sequence: (1) introduce `gradle/libs.versions.toml`, migrating `gradle.properties` versions (Renovate keeps working); (2) move buildSrc to `build-logic/` convention plugins; (3) enable configuration cache in CI and fix violations; (4) convert `.gradle` → `.gradle.kts` file-by-file. Do not wait for Declarative Gradle.
- Moving versions out of `gradle.properties` into a catalog also gives typed `libs.*` accessors in Kotlin DSL, which is where most of the IDE benefit comes from.

### Gaps
- No primary 2026 Gradle statement on Groovy DSL deprecation was found. As of the sources above, Groovy DSL is not deprecated.
- No published migration report was found for a Gradle build of uPortal's size and shape (WAR + portlet overlays + custom deploy tasks).
- No OpenRewrite recipe for Groovy→Kotlin DSL was found (see Q4).

## 3. Replacements for legacy components (keep / upgrade / replace, with migration paths)

### Takeaway
Most components have a clear Jakarta-era successor: Ehcache 2 → JCache-backed caches (Ehcache 3 or Infinispan), Joda → `java.time`, springfox → springdoc v3, jasypt → Spring Security `DelegatingPasswordEncoder`, Lucene 8 → 10 (with reindex), JAXB 2.3 → JAXB 4, Vue 2 → Vue 3/Lit, Groovy 3 → Groovy 5. Five need real design work rather than a version bump:
- **Clustered caching.** Ehcache 3 has no JGroups/RMI replication; only Terracotta clustering. Infinispan embedded (JGroups, invalidation mode) is the closest functional replacement.
- **Spring Web Flow in portlets.** SWF 4.0.1 runs on Spring 7, but SWF dropped portlet support in 2.5, so the 26 portlet flows must be rewritten.
- **Schema management.** Liquibase 5 is FSL-licensed and has Hibernate 7 diff support. Flyway OSS is Apache 2.0 but SQL-per-vendor.
- **Dev SSO.** Use the CAS 8 Docker image rather than a bundled CAS 3.6 WAR.
- **Dev DB / CI.** Testcontainers covers PostgreSQL, MySQL/MariaDB, SQL Server and Oracle Free.

### Cited Findings

#### 3a. Caching: Ehcache 2.6 + JGroups 3.6 replication
- Spring Framework 6.0 removed the `org.springframework.cache.ehcache` package (Ehcache 2.x support): "using Ehcache through the JCache API or its new native API is preferred." — [Spring Framework 6.0 Release Notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-6.0-Release-Notes)
- The Hibernate ORM user guide (main branch) documents only two 2LC integrations: JCache via `hibernate-jcache` (plus a JSR-107 provider) and Infinispan. Config: `hibernate.cache.region.factory_class=jcache`, `hibernate.javax.cache.provider` (e.g., `org.ehcache.jsr107.EhcacheCachingProvider`), `hibernate.javax.cache.uri`, and `hibernate.javax.cache.missing_cache_strategy` (`create-warn` default, `fail`, `create`). It warns that recent Ehcache versions enable disk persistence for default caches, so caches should be explicitly configured. Query cache regions: `default-query-results-region` and `default-update-timestamps-region`. The timestamps region should have no expiry or eviction. — [Hibernate Caching.adoc source](https://raw.githubusercontent.com/hibernate/hibernate-orm/main/documentation/src/main/asciidoc/userguide/chapters/caching/Caching.adoc)

### Inferences
- **Caching recommendation.**
  - Ehcache 3 cannot reproduce uPortal's Ehcache 2 + JGroups peer replication without running a Terracotta server, which is a new operational component for every adopter.
  - The closest drop-in is **Infinispan embedded**. It uses JGroups (already a uPortal concept), offers invalidation mode for DB-backed data, has a Hibernate 7.1+ 2LC module (`infinispan-hibernate-cache-v66`) and can serve app-level caches via its own API or JCache.
  - A lighter alternative: Caffeine (local, via Spring Cache or JCache) for the many purely local caches, plus an explicit invalidation channel (JGroups, DB polling or Redis pub/sub) for the few regions that need cluster coherence. Infinispan in `local` mode can also play the Caffeine role.
- **Ehcache API rewrite.** The 58 files using `net.sf.ehcache` directly (SelfPopulatingCache, Search API) need rewriting whatever the provider. Map SelfPopulatingCache to read-through (`CacheLoader`/`CacheLoaderWriter` in JCache/Ehcache 3, `LoadingCache` in Caffeine, or Spring `@Cacheable(sync=true)`). Ehcache 2's Search API has no equivalent in JCache/Caffeine; replace with in-memory indexes or DB queries. This mapping is inference; the Ehcache 3 migration guide fetched only covers per-mapping expiry.
- **Introduce a facade.** First route uPortal's code through Spring's `CacheManager`/`Cache` abstraction (replacing spring-modules-cache with `@Cacheable`). After that, the provider (Infinispan, Ehcache 3, Caffeine) becomes configuration, and the 184 regions can be generated into one provider config.
- **Joda migration path:**
  1. Run rewrite-joda `NoJodaTime` (accept the Moderne license or run via Moderne).
  2. Fix the residuals by hand.
  3. Replace Jadira `PersistentDateTime` etc. with native Hibernate `java.time` mappings: `Instant` or `LocalDateTime` for TIMESTAMP columns, `OffsetDateTime` only where an offset column exists.
  4. Pin `hibernate.jdbc.time_zone` (e.g., UTC, if Jadira was configured to store UTC) and `hibernate.timezone.default_storage=NORMALIZE` (or `NORMALIZE_UTC`) so existing column types and semantics stay unchanged.
  5. Verify with `hbm2ddl validate` / schema diff on all five DBs. Jadira's actual stored zone (JVM default vs UTC) must be checked in uPortal's config before choosing.
- **Spring Web Flow.** Upgrading to SWF 4.0.1 is only viable if the admin flows run as servlet (not portlet) flows. Since portlet support left SWF in 2.5, the 26 portlet-hosted flows must be rewritten whatever happens. Options:
  - (a) Plain Spring MVC/annotated portlet controllers with session-scoped form state. Lowest dependency risk.
  - (b) htmx-enhanced server-rendered pages served by uPortal's servlet side.
  - (c) A client-side admin SPA or web components over REST.
  Converting to servlet-side SWF 4 flows is possible but keeps a niche framework with recent CVEs.
- **Password hashes.** Configure `DelegatingPasswordEncoder` with a custom `{md5}`/`{jasypt}` legacy matcher for uPortal's existing format (or `setDefaultPasswordEncoderForMatches`), plus a `UserDetailsPasswordService` that writes back a bcrypt/argon2 hash on successful login. Hashes still on MD5 after a grace period should get forced resets.
- **Schema management.**
  - Liquibase is technically the better fit for a five-vendor product (XML/YAML changesets with abstract types, plus liquibase-hibernate diffs against the Hibernate 7 model for each release). Its FSL licence is not OSI-open source, though, and Apereo/uPortal adopters' legal teams may object.
  - Flyway OSS (Apache 2.0) would need vendor-specific SQL folders (`db/migration/{postgresql,mysql,oracle,sqlserver,hsqldb}`) plus `baselineOnMigrate` at a "6.0.0 baseline" version.
  - Either way, baseline as follows: generate the 6.0 schema once per vendor from Hibernate (SchemaExport) or via `generateChangeLog`, mark existing 5.x→6.0 upgraded DBs as baselined, then use migration-only DDL afterwards.
  - Note that Liquibase Community 5.x no longer bundles JDBC drivers or extensions, so the build must add them explicitly.
  - Whether Liquibase changesets are more vendor-neutral than Flyway's SQL comes from general product knowledge, not from a source fetched here.
- **Dev DB.** Keep an in-process DB only for quick demos. Use Testcontainers PostgreSQL as the default dev/CI DB, and run a CI matrix (PostgreSQL, MySQL/MariaDB, SQL Server, Oracle Free) that restores a 5.x schema dump and runs the 6.0 upgrade. This is what makes in-place upgrade testing practical.
- **Lucene.**
  - Upgrade to Lucene 10.x, which needs Java 21+ (fine on Java 25). Fix the API breaks listed above.
  - Treat the index as derived data and **rebuild on first start**. An 8.x-created index is only best-effort readable in Lucene 10 with backward-codecs, is not writable by IndexWriter, and the "segment created with Lucene 7 or newer" condition may fail for old indexes.
- **JAXB.** A straight namespace switch to JAXB 4 (jakarta) plus xjc-gradle-plugin. Existing XML import/export *data files* use XML namespaces and schemas, not Java packages, so they should stay compatible, but this needs a round-trip test.
- **Local SSO.**
  - The lightest option that keeps CAS as the documented production integration is to replace the bundled CAS 3.6 WAR with the official `apereo/cas:v8.0.x` Docker image (or a minimal CAS 8 overlay) in a Docker Compose dev stack, with uPortal using java-cas-client 4.x.
  - Keycloak would need a third-party CAS extension or a switch to OIDC, which changes the integration being tested.
  - A plain Spring Security form login profile could be offered as a "no-SSO" fallback for the quickest demos.
- **Web components.** No sign of a Vue 3 port of uPortal-web-components; the last dated release was 2023 and the Node 14 engine is EOL. Port each component to Vue 3 (`defineCustomElement`) or Lit. Lit is lighter for standalone custom elements, but this has no source here.
- **Groovy shell.** Move to Groovy 5 (supports JDK 25). JShell is an option only if scripts are rewritten in Java syntax, and it cannot reuse the Groovy DSL helpers.
- **Dev environment.** Replace uPortal-start's custom Gradle Tomcat/HSQLDB/CAS tasks with a Docker Compose stack (Tomcat 11 + Postgres + CAS 8). Keep Gradle tasks only for building and deploying artifacts into a mounted Tomcat volume.

### Gaps
- No primary Ehcache 3 statement was found saying "no JGroups/RMI replication". The conclusion rests on the module list.
- Redisson and Hazelcast Hibernate 7 native support were not verified. Hibernate 7.0 with Infinispan (vs 7.1+) was not confirmed.
- How Jadira is configured in uPortal (`jadira.usertype.databaseZone` / `javaZone`) was not checked. It is essential for preserving timestamp semantics and is assigned to the codebase inventory notes.
- springdoc's official compatibility matrix (springdoc.org) and its "migrating from springfox" guide were not fetched (DNS).
- Flyway 11/12 per-database Community-edition matrix for Oracle/MySQL was not confirmed. Liquibase FSL acceptability under Apereo licensing policy was not researched.
- No evidence found for HSQLDB vs H2 compatibility with uPortal's schema, or for Testcontainers `oracle-free` image timings in CI.
- CAS Docker image default credentials (`casuser`/`Mellon`) were only confirmed for a third-party image, not for `apereo/cas`.
- Groovy 3 compatibility with Java 25 and Groovy 4 EOL policy were not found. JShell was not researched.
- Vue 3 `defineCustomElement` and Lit were not researched with primary sources.
- json-lib → Jackson 3 was not researched in depth. The only finding is that Boot 4 prefers Jackson 3 (`tools.jackson` packages).

## 4. Automated migration tooling (OpenRewrite, Eclipse Transformer, Tomcat jakartaee-migration)

### Takeaway
OpenRewrite covers Java-source and build-file migrations well: Spring Boot 4 / Spring Framework 7 / Security 7, Jakarta EE 9–11 dependency and namespace changes, web.xml / web-fragment.xml, JAXB, and Joda→java.time (rewrite-joda, source-available license). It has no JSP parser, no Spring XML bean-definition recipes and no Groovy→Kotlin DSL recipe. For JSPs, TLDs, XML contexts and binary third-party jars/WARs, use the Tomcat jakartaee-migration tool or Eclipse Transformer, or plain text replacement, and verify with tests.

### Cited Findings
- `org.openrewrite.java.spring.boot4.UpgradeSpringBoot_4_0` ("Community Edition") chains Boot 3.5 prep, `org.openrewrite.java.spring.framework.UpgradeSpringFramework_7_0`, Spring Security 7.0, Spring Batch 6.0, Spring Cloud 2025.1, Boot 4.0 property migration and `@MockBean`→`@MockitoBean`. A similarly named recipe exists under `io.moderne`. Review diffs, because OpenRewrite "can't know your API contracts or deployment assumptions". — [OpenRewrite UpgradeSpringBoot_4_0](https://docs.openrewrite.org/recipes/java/spring/boot4/upgradespringboot_4_0-community-edition); [OpenRewrite 8.66.1 changelog](https://docs.openrewrite.org/changelog/8-66-1-Release); [Vaadin migration playbook](https://blog.vaadin.com/spring-boot-4-migration-playbook-for-teams-upgrading-from-3.5)
- rewrite-migrate-java Jakarta recipes: `jakarta-ee-9.yml` (javax→jakarta artifact/package moves, incl. `jakarta.servlet.jsp-api` and Jetty `jetty-ee9-apache-jsp`), `jakarta-ee-10.yml` (Servlet 6.0, JSP 3.1), `jakarta-ee-11.yml` (JSP API 4.0.x). Individual XML recipes: `JavaxWebXmlToJakartaWebXml` (web-app 6.0 namespace), `web-fragment.xml`, `persistence.xml`, `faces-config.xml` and taglib.xml (Faces). JSTL URI changes inside Faces files use `org.openrewrite.text.FindAndReplace` (e.g., `http://java.sun.com/jsp/jstl/core` → `jakarta.tags.core`). — [GitHub code search: rewrite-migrate-java META-INF/rewrite](https://github.com/openrewrite/rewrite-migrate-java/tree/main/src/main/resources/META-INF/rewrite); [JavaxWebXmlToJakartaWebXml](https://docs.openrewrite.org/recipes/java/migrate/jakarta/javaxwebxmltojakartawebxml)
- A recipe that rewrites `*.tld` files (taglib version 3.0, Jakarta namespace, `javax.`→`jakarta.`) exists in the **Oracle WebLogic** recipe set, not in core rewrite-migrate-java. — [OpenRewrite WebLogic TLD recipe](https://docs.openrewrite.org/recipes/oracle/weblogic/rewrite/jakarta/javaxwebjsptaglibrarytldstojakarta9webjsptaglibrarytlds)
- No Spring XML (`beans`/`applicationContext`) recipes were found in rewrite-spring's recipe YAMLs (GitHub code search returned zero hits). — [GitHub code search rewrite-spring META-INF/rewrite](https://github.com/openrewrite/rewrite-spring)
- Joda: `NoJodaTime` now lives in rewrite-joda (extracted in rewrite-migrate-java 3.16.0) and is Moderne Source Available licensed. It is also referenced in rewrite-migrate-java's `java-best-practices.yml`. — [OpenRewrite NoJodaTime](https://docs.openrewrite.org/recipes/java/joda/time/nojodatime); [rewrite-migrate-java java-best-practices.yml](https://github.com/openrewrite/rewrite-migrate-java/blob/main/src/main/resources/META-INF/rewrite/java-best-practices.yml)
- No OpenRewrite recipe for Gradle Groovy DSL → Kotlin DSL was found. Official guidance is manual and incremental, with IntelliJ assistance. — [Gradle migration guide](https://docs.gradle.org/current/userguide/migrating_from_groovy_to_kotlin_dsl.html); [JetBrains help](https://www.jetbrains.com/help/idea/migrate-gradle-build-scripts-to-kotlin-dsl.html.md)
- Tomcat jakartaee-migration converts "package references in classes, String constants, configuration files, JSPs, TLDs etc." in archives, folders or single files. It renames only Java EE packages and strips JAR signatures. It runs as a CLI (`java -jar jakartaee-migration-*-shaded.jar <src> <dest>`), an Ant task (`profile="tomcat"`) or the `javax2jakarta` distro package, and is invoked automatically by Tomcat 11's `legacyAppBase`. — [apache/tomcat-jakartaee-migration](https://github.com/apache/tomcat-jakartaee-migration); [Tomcat 11 host.xml docs source](https://raw.githubusercontent.com/apache/tomcat/11.0.x/webapps/docs/config/host.xml)

### Inferences
- Suggested tool split for uPortal:
  - OpenRewrite (rewrite-spring `UpgradeSpringBoot_4_0` or `UpgradeSpringFramework_7_0`, rewrite-migrate-java `JakartaEE11`, rewrite-hibernate, rewrite-joda) for Java sources and Gradle dependency coordinates.
  - The Tomcat migration tool in directory mode, or scripted `sed`, for the 111 JSPs, TLDs, `web.xml` and 113 Spring XML files. Spring XML bean class names and `javax.*` property types are plain strings that OpenRewrite's Java recipes won't touch.
  - Manual review for Spring XML schema changes (removed `spring-*` XSD elements, e.g. `cache:`/`webflow` portlet configs).
- The Tomcat migration tool is best used for third-party binaries that won't be rebuilt. For uPortal's own sources, source-level migration is preferable, because the tool also rewrites string constants and can over-match.
- Eclipse Transformer would serve the same binary-rewrite role and is configurable via rule files. This is general knowledge only; it was not researched here (see Gaps).
- Groovy→Kotlin DSL conversion stays manual or IDE-assisted. Budget it as engineering time, not tooling.

### Gaps
- Eclipse Transformer was not researched (no sources fetched); its current version and JSP/TLD handling are unverified.
- Whether any OpenRewrite recipe parses JSP files (beyond text find/replace) is unconfirmed; the evidence suggests not.
- The exact recipe names in the current rewrite-spring release (e.g., `UpgradeSpringFramework_7_0` vs `_7`) should be checked against the pinned version.
- OpenRewrite coverage for Ehcache 2→3/JCache, SWF, springfox→springdoc and Lucene 8→10 was not investigated. No such recipes surfaced in searches.
