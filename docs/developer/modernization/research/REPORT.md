# Moving uPortal to Jakarta without losing portlets

uPortal can be upgraded to Java 25, Gradle 9.8, Spring Framework 7.0, Spring Security 7, Hibernate ORM 7.4 and Tomcat 11, and Apereo CAS 8.0 already runs almost exactly that stack in production. The framework APIs are not where the time goes. The long poles are the portlet layer and the in-place database upgrade. uPortal has no Jakarta portlet container it could simply adopt, and Hibernate 6/7 dialects quietly change how IDs are generated on SQL Server and MariaDB. The recommended route has eight phases and about fifty small PRs, and it follows the Spring/Hibernate support pairs already chosen in MOD-D5. Everything that can be done while still on javax should be done first: the toolchain, Hibernate 5.x, a vendored Spring Portlet MVC, an in-tree Pluto, moving cache access onto the JCache API, Joda removal and the Spring Security 5.8 toggles. After that, four steps cannot be split further. The largest of them has to land across repositories at once: switching uPortal, uPortal-start's shared libraries and every deployed portlet WAR from javax to jakarta together. With the earlier work done, that step is mechanical and scripted. Existing JSR-286 WARs can keep running on Tomcat 11, but only through a hybrid that uPortal maintains itself. It consists of Pluto 2.1 moved onto jakarta.servlet inside the uPortal tree, a javax.portlet 2.0 API recompiled against jakarta.servlet, and a build-time transformation of each WAR. That is the same pattern Sakai merged on 9 October 2026. It keeps those WARs running until they are replaced, and the bundled portlets should become REST services plus custom elements during 6.x. Production databases can upgrade without manual SQL if 6.0 does four things: freeze Hibernate 4.3-era DDL behaviour with documented legacy settings and dialect subclasses, prove zero DDL drift on all five database vendors with Testcontainers, accept upgrades only from 5.17.x, and use Flyway (Apache-2.0) rather than Liquibase 5 (FSL) for future migrations. An external Tomcat 11 is still the right runtime, and Kotlin DSL can wait until after 6.0. The biggest risk is upstream. A Jakarta 6.0 merges the published uP6 and uP7 scopes and contradicts the April 2025 "Java 17 on Tomcat 9" direction and the current Renovate pins. Upstream also depends on one maintainer who performs about 95% of merges. So community agreement has to come before the large PRs. This report proposed an RFC in `uPortal-Project/community` for it. Each decision is now proposed as an ADR instead ([ADR index](../../adr/README.md), MOD-D36).

## Spring 7, Hibernate 7.4 and Tomcat 11 move only as a bloc

Each Spring generation fixes the Java level, the namespace, the Servlet level (and so the Tomcat version), the JPA level (and so the Hibernate version) and the Jackson generation. Spring Framework 7.0 keeps a JDK 17 baseline but recommends JDK 25. It moves to Jakarta EE 11, which means **Servlet 6.1 (Tomcat 11.0, Jetty 12.1)** and **JPA 3.2 (Hibernate ORM 7.1/7.2)**, and it drops Undertow because Undertow lacks Servlet 6.1 ([Spring Framework 7.0 release notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-7.0-Release-Notes)). Open-source support for **Spring 6.2 ended in June 2026** and for 5.3 in August 2024, so 7.x is the only OSS-supported landing zone. 7.1 follows in November 2026 ([Spring Framework Versions](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-Versions)). So every intermediate Spring stop is a test checkpoint and not something to release. MOD-D5 treats the 6.2 + 6.6 stop exactly this way ([LOG.md](../LOG.md)).

Hibernate's newest stable release is **7.4.12.Final**. 8.0 is still at Beta3 and targets JPA 4.0 ([Maven Central hibernate-core](https://repo1.maven.org/maven2/org/hibernate/orm/hibernate-core/maven-metadata.xml)). Spring 7.0 officially names Hibernate 7.1/7.2. Spring Boot 4.1 pairs Spring 7.0 with Hibernate 7.4 ([Hibernate 7.4 series data](https://github.com/hibernate/hibernate.org/blob/production/_data/projects/orm/releases/7.4/series.yml)), and **CAS 8.0.x runs Spring 7.0.8, Hibernate 7.4.5, Tomcat 11.0.26, Spring Security 7.1.0 and Spring Web Flow 4.0.1 on Java 25** ([CAS 8.0.x libs.versions.toml](https://raw.githubusercontent.com/apereo/cas/8.0.x/gradle/libs.versions.toml)). That combination is production-proven inside Apereo, so targeting 7.4 directly is safer than the literal 7.1/7.2 wording suggests. The pairing also explains why the path has stepping stones. Spring 4.3 tops out at Hibernate 5.2. Spring 5.3 is built around Hibernate 5.4 and runs 5.6 ([Spring 4.x upgrade notes](https://github.com/spring-projects/spring-framework/wiki/Upgrading-to-Spring-Framework-4.x), [Spring 5.3 release notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-5.3-Release-Notes)). Spring 6 requires either the Hibernate 5.6 `-jakarta` artifacts or 6.1+ ([Spring 6.0 release notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-6.0-Release-Notes)).

The runtime and build constraints come along with this. JDK 25 has been the LTS since 16 September 2025, and the next LTS (29) is due September 2027 ([InfoQ](https://www.infoq.com/news/2025/08/java-25-so-far)). Free vendor support for 25 runs to October 2032 (Corretto) and September 2033 (Azul), while Temurin 11 ends in October 2027 ([Corretto FAQ](https://aws.amazon.com/corretto/faqs/), [Azul Zulu 25 notes](https://docs.azul.com/core/pdfs/25-ga/azul-zulu-ca-release-notes-25-ga-rev1.0.pdf)). Tomcat 8.5 has been EOL since March 2024. Tomcat 9.0 support ends on **31 March 2027**, with a 9.1.x branch receiving releases until 2030. Tomcat 11.0.26 needs Java 17 ([Tomcat 9.0 end of support](https://raw.githubusercontent.com/apache/tomcat-site/trunk/xdocs/tomcat-9.0.x-eos.xml), [Tomcat whichversion](https://raw.githubusercontent.com/apache/tomcat-site/trunk/xdocs/whichversion.xml)). Gradle 9.8.1 is current. Its daemon needs a JVM between 17 and 27, Java 11 can run Gradle only up to 8.14.x, and toolchains have supported Java 25 since 9.1 ([Gradle compatibility matrix](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/releases/compatibility.adoc)).

The bloc logic determines how the plan is structured. Anything tied to a Spring generation (Security, Session, Web Flow, LDAP, Hibernate, Servlet level) has to cross each boundary together with Spring. Anything not tied to one (Gradle, JUnit/Spock/Groovy, Joda, the cache API, the portlet framework fork, the Pluto source import, schema tooling) can and should cross on its own and ahead of time. Each boundary PR is then as small as possible.

## Hibernate's API breaks are mechanical; its data changes are not

uPortal's Hibernate code is less exposed than its size suggests. There are 61 entities, 342 `org.hibernate` import lines in 91 files, **no legacy Criteria API**, JPA Criteria dominate (64 `createCriteriaQuery` calls in 27 files), there are about five HQL strings and no native queries ([persistence inventory](./codebase_inventory_persistence.md)). Because of that, the query-semantics changes in 6.0, 6.3 and 7.3 are a contained risk. Those changes drop association-to-FK comparison and special handling of `= null`, and they make `getSingleResult()` strict ([Hibernate 6.0 migration guide](https://github.com/hibernate/hibernate-orm/blob/6.0/migration-guide.adoc), [6.3](https://github.com/hibernate/hibernate-orm/blob/6.3/migration-guide.adoc), [7.3](https://github.com/hibernate/hibernate-orm/blob/7.3/migration-guide.adoc)). A startup test that parses every HQL/JPQL string through `createQuery` catches them.

The expensive code is in a few places. The first is the **schema tooling behind `dataInit`** (MOD-I1). `DataSourceSchemaExport`, `HibernateDbLoader` and `FixedDatabaseMetadata` use `Configuration.generateSchemaCreationScript`, `buildMapping` and `Table.sqlCreateString`, all of which were removed in 5.0 when bootstrapping moved to `MetadataSources`. Schema tooling was then unified with JPA schema generation in 5.1 ([5.0 guide](https://github.com/hibernate/hibernate-orm/blob/5.0/migration-guide.adoc), [5.1 guide](https://github.com/hibernate/hibernate-orm/blob/5.1/migration-guide.adoc)). The second is a set of **classes uPortal places inside Hibernate's own packages**: `SpringBeanEhCacheRegionFactory`, which breaks under the 5.3 second-level-cache SPI redesign, and `FixedDatabaseMetadata`. The third is the **type system**: nine UserTypes, `global.hbm.xml` typedefs, 32 string-based `@Type` references, and Jadira's Joda mappings. `@TypeDef` and string `@Type` disappear in 6.0, the `UserType` signatures change again in 7.0, and **Jadira's last release is a 2018 CR with no Hibernate 6 support** ([6.0 guide](https://github.com/hibernate/hibernate-orm/blob/6.0/migration-guide.adoc), [7.0 guide](https://github.com/hibernate/hibernate-orm/blob/7.0/migration-guide.adoc), [Jadira on Maven Central](https://repo1.maven.org/maven2/org/jadira/usertype/usertype.core/maven-metadata.xml)). The fourth is the **annotations 7.0 removes**, which are Hibernate `@Index` (49 uses in 10 files), `@IndexColumn` (4) and `@LazyCollection` (2). JPA `@Table(indexes=…)` with the same explicit names, `@OrderColumn` and plain JPA fetch settings replace them, and all of those replacements already work on 5.2. Finally, `persistence.xml` uses `hibernate.ejb.cfgfile`, which 6.0 renames to `hibernate.cfg_xml_file`, and `jmxContext.xml` calls `HibernateEntityManagerFactory.getSessionFactory()`. Smaller 7.0 traps follow. Classpath scanning needs `hibernate-scan-jandex`, and the SessionFactory takes its name from the persistence unit and may try JNDI binding. Bulk updates of `@Immutable` entities throw, and persisting a detached instance through cascade throws `EntityExistsException` ([7.0 guide](https://github.com/hibernate/hibernate-orm/blob/7.0/migration-guide.adoc)). OpenRewrite's `MigrateToHibernate60`…`70` recipes handle the mechanical renames. They have **no 4.x→5.x recipes**, cannot resolve hbm typedef aliases such as `"fname"`, and are published under the Moderne Source Available License rather than Apache ([rewrite-hibernate license](https://github.com/openrewrite/rewrite-hibernate/blob/main/LICENSE.md)). They are useful only as local tools whose diffs get reviewed (MOD-I28).

### ID generators on SQL Server and MariaDB are the sharpest edge

The success criterion is that "existing PostgreSQL, MySQL/MariaDB, Oracle and SQL Server databases upgrade in place without manual SQL", and that criterion is decided mostly by identifier generation. Forty-nine uPortal entities declare both a `@SequenceGenerator` and a `@TableGenerator` under the same name, with allocation sizes from 1 to 10,000 ([persistence inventory](./codebase_inventory_persistence.md)). In 4.3, 5.6 and 6.6 the sequence definition takes precedence, because it is registered after the table generator ([AnnotationBinder 4.3](https://github.com/hibernate/hibernate-orm/blob/4.3/hibernate-core/src/main/java/org/hibernate/cfg/AnnotationBinder.java), [GeneratorBinder 6.6](https://github.com/hibernate/hibernate-orm/blob/6.6/hibernate-core/src/main/java/org/hibernate/boot/model/internal/GeneratorBinder.java)). On a dialect without sequences, that sequence-style generator falls back to a table. uPortal's `PortalDialectResolver` forces `SQLServer2005Dialect`, and MariaDB is detected as MySQL, so on both of those databases the `UP_*_SEQ` objects are most likely tables. This is inferred from dialect behaviour and has not yet been checked on a real database (MOD-I23). In 7.4, however, **`SQLServerDialect` always reports sequence support and `MariaDBDialect` returns `MariaDBSequenceSupport`**, while `MySQLDialect` still has no sequence support ([SQLServerDialect 7.4](https://github.com/hibernate/hibernate-orm/blob/7.4/hibernate-core/src/main/java/org/hibernate/dialect/SQLServerDialect.java), [MariaDBDialect 7.4](https://github.com/hibernate/hibernate-orm/blob/7.4/hibernate-core/src/main/java/org/hibernate/dialect/MariaDBDialect.java), [MySQLDialect 7.4](https://github.com/hibernate/hibernate-orm/blob/7.4/hibernate-core/src/main/java/org/hibernate/dialect/MySQLDialect.java)). So an unmodified upgrade either fails on missing sequences or, worse, starts numbering again from a fresh sequence. Increment validation adds a second failure mode. Since 5.4, startup fails by default when a database sequence's increment differs from the mapping's `allocationSize` ([AvailableSettings 5.6](https://github.com/hibernate/hibernate-orm/blob/5.6/hibernate-core/src/main/java/org/hibernate/cfg/AvailableSettings.java)). The 4.3 upgrade in PR #3012 already had to switch `POOLED` to `POOLED_LO` to keep ID semantics intact ([uPortal commit fafb9b6ef](https://github.com/uPortal-Project/uPortal/commit/fafb9b6ef)), which shows how easily these semantics drift.

The fix that meets the no-manual-SQL criterion is a pair of thin dialect subclasses for SQL Server and MariaDB that don't report sequence support, which keeps the table-backed generators exactly as they are. A one-time automated conversion can follow in 6.x as a Flyway Java migration. Hibernate 7.2+ also offers `SchemaManager.resynchronizeGenerators()` as a safety net, but Hibernate marks it as not yet stable ([SchemaManager 7.4](https://github.com/hibernate/hibernate-orm/blob/7.4/hibernate-core/src/main/java/org/hibernate/relational/SchemaManager.java)). The dead `@TableGenerator` declarations should be removed early. Doing it in phase 2 on Hibernate 5.2, behind the database harness, means 7.0's stricter generator validation can never resolve the name to the wrong definition ([7.0 guide](https://github.com/hibernate/hibernate-orm/blob/7.0/migration-guide.adoc)).

### The remaining data risk is in LOBs, time zones and constraint names

On PostgreSQL, Hibernate up to 5.6.1 created `text` columns but stored large-object OIDs in them. 5.6.2 switched to `oid`, and **`vacuumlo` can delete LOBs referenced only from `text` columns, which loses data** ([5.6 guide](https://github.com/hibernate/hibernate-orm/blob/5.6/migration-guide.adoc)). Releases 5.2.9 and 5.2.10 stored PostgreSQL LOB strings in a way that neither earlier nor later versions can read, so the 5.2 hop must target 5.2.18 or later ([5.2 guide](https://github.com/hibernate/hibernate-orm/blob/5.2/migration-guide.adoc)). `PortletPreferenceImpl.PREF_VALUE` is mapped as `@Lob` with a `@Type(StringType)` override that 6.0 removes. Unless it gets an explicit `@JdbcTypeCode` or `columnDefinition`, the column silently becomes a CLOB/oid (MOD-I25). On time zones, 6.2 switched `hibernate.timezone.default_storage` to native offset storage, and `NORMALIZE` restores the 5.x behaviour ([6.2 guide](https://github.com/hibernate/hibernate-orm/blob/6.2/migration-guide.adoc)). Jadira's `databaseZone=jvm` semantics for `LocalDate` must be reproduced exactly by whatever replaces it. Constraint names need care as well. 4.3 named foreign keys `FK_` plus a hash, while 5.x hashes them differently even under the legacy implicit-naming strategies, because those strategies extend the JPA-compliant one ([Constraint 4.3](https://github.com/hibernate/hibernate-orm/blob/4.3/hibernate-core/src/main/java/org/hibernate/mapping/Constraint.java), [ImplicitNamingStrategyJpaCompliantImpl 5.6](https://github.com/hibernate/hibernate-orm/blob/5.6/hibernate-core/src/main/java/org/hibernate/boot/model/naming/ImplicitNamingStrategyJpaCompliantImpl.java)). Users report that running `hbm2ddl update` against a 4.x schema created **duplicate foreign keys under new names** ([Hibernate forum](https://forum.hibernate.org/viewtopic.php?p=2491838)). The rule follows directly: 6.0 must never run `hbm2ddl update` against an upgraded database, and schema equality has to be measured with hashed constraint names normalized.

Minimum database versions are part of the adopter contract too. Hibernate 7.4 requires PostgreSQL 14, MariaDB 10.6, SQL Server 2014 (12.0), Oracle 19, MySQL 8 and HSQLDB 2.6.1. Anything older needs `hibernate-community-dialects` ([PostgreSQLDialect 7.4](https://github.com/hibernate/hibernate-orm/blob/7.4/hibernate-core/src/main/java/org/hibernate/dialect/PostgreSQLDialect.java), [6.2 guide](https://github.com/hibernate/hibernate-orm/blob/6.2/migration-guide.adoc)). uPortal-start's HSQLDB 2.5.1 is already below that floor (MOD-I27).

### Freeze the old behaviour, prove zero drift, then thaw deliberately

MOD-I26 proposes a block of settings to "freeze 5.x behaviour", and the research makes it concrete. Every 6.x/7.x default change that affects existing columns has a documented switch. The block should be: `hibernate.implicit_naming_strategy=legacy-jpa`, or `legacy-hbm`, whichever the DDL diff selects. `hibernate.id.db_structure_naming_strategy=legacy`. `hibernate.timezone.default_storage=NORMALIZE`. `hibernate.type.preferred_instant_jdbc_type=TIMESTAMP`. `hibernate.type.preferred_duration_jdbc_type=BIGINT`. `hibernate.type.wrapper_array_handling=legacy`. `hibernate.type.preferred_array_jdbc_type=VARBINARY`. On Oracle add `hibernate.dialect.oracle.use_binary_floats=false`, `hibernate.dialect.oracle.value_lob_enabled=false` and, on Oracle 23, `preferred_boolean_jdbc_type=BIT`. Finish with `hibernate.query.native.prefer_jdbc_datetime_types=true` and `hibernate.cache.query_cache_layout=SHALLOW`. During the 5.x hops, also set `hibernate.id.generator.stored_last_used=false` ([5.3 guide](https://github.com/hibernate/hibernate-orm/blob/5.3/migration-guide.adoc), [6.0 guide](https://github.com/hibernate/hibernate-orm/blob/6.0/migration-guide.adoc), [7.0 guide](https://github.com/hibernate/hibernate-orm/blob/7.0/migration-guide.adoc), [7.4 guide](https://github.com/hibernate/hibernate-orm/blob/7.4/migration-guide.adoc)). Whether each setting works is something the database harness proves, not something to assume. The harness restores a 5.17 dump on each vendor using the Testcontainers modules for PostgreSQL, MySQL, MariaDB, SQL Server and Oracle Free ([Testcontainers modules](https://github.com/testcontainers/testcontainers-java/tree/main/modules)). It then boots the candidate build with schema validation, diffs the generated DDL against the 5.17 DDL with constraint names normalized, inserts one row of every entity to check that generators keep numbering past `max(id)`, and round-trips every custom-typed column under a non-UTC JVM time zone.

For MOD-Q4 the decision is driven by licensing rather than technology. Liquibase is the better tool for five database vendors, and liquibase-hibernate already diffs against Hibernate 7.4 ([liquibase-hibernate releases](https://github.com/liquibase/liquibase-hibernate/releases)). However, **Liquibase Community 5.0 moved to the Functional Source License** ([Liquibase blog](https://www.liquibase.com/blog/liquibase-community-for-the-future-fsl)), which is not OSI open source and is a poor fit for an Apache-2.0 Apereo project. Flyway OSS is Apache-2.0 and supports `baselineOnMigrate` for existing schemas ([Flyway README](https://github.com/flyway/flyway), <!-- vale ai-tells.ColonUsage = NO --><!-- citation link text kept verbatim -->[Redgate: Baseline On Migrate](https://documentation.red-gate.com/fd/baseline-on-migrate-224919695.html)<!-- vale ai-tells.ColonUsage = YES -->). So the 6.0 design should use Hibernate-generated DDL for fresh installs, with `dataInit` ported first to the 5.x `MetadataSources` APIs and later to `SchemaManager`. Zero DDL drift should be the upgrade mechanism, and Flyway with a 5.17 baseline should be the place for future, explicit, mostly Java-based migrations. One of those migrations is the deliberate thaw of individual freeze settings after 6.0.

## Spring's removals fall on portlets, caches, Joda and Jackson

For a WAR configured through 113 XML contexts, most Spring hops are cheap. The cost is in a few integrations that Spring removed. Spring 5.0 dropped Portlet support entirely and suggested that projects needing it create "custom adapter classes in your own project (possibly derived from Spring Framework 4.x)". In the same release it dropped `orm.hibernate3/4`, `Log4jConfigurer`, the servlet `AnnotationMethodHandlerAdapter`, and the commons-logging dependency in favour of `spring-jcl` ([Spring 5.0 release notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-5.0-Release-Notes)). Spring 5.3 stopped suffix pattern matching by default ([5.3 notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-5.3-Release-Notes)). Spring 6.0 removed Ehcache 2 support, Joda-Time formatting, `CommonsMultipartResolver`, `HandlerInterceptorAdapter` and HTTP Invoker, made `PathPatternParser` the default, set trailing-slash matching to false and required HttpClient 5 ([6.0 notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-6.0-Release-Notes)). Spring 6.1 removed `LocalVariableTableParameterNameDiscoverer`. Without **`-parameters`**, name-based `<constructor-arg name=…>`, implicit `@RequestParam`/`@PathVariable` names and `#param` SpEL then fail at runtime ([6.1 notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-6.1-Release-Notes)). Bean classes in third-party jars compiled without the flag cannot be fixed by uPortal's compiler options, so those XML definitions need `index=` or `type=`. Spring 6.2 rewrote the placeholder parser, so keys containing `:` must be escaped, and it tightened autowiring ([6.2 notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-6.2-Release-Notes)). Spring 7.0 **stopped recognising `javax.annotation` and `javax.inject`**, which affects uPortal's 31 `@PostConstruct` and 28 `@Resource` uses. It also moved native Hibernate support to `orm.jpa.hibernate`, replaced `spring-jcl` with commons-logging 1.3 (which collides with `jcl-over-slf4j` unless one is excluded), removed the suffix and trailing-slash options outright, deprecated the `<mvc:*>` namespace and JUnit 4 support, and **made Jackson 3 the default**. Jackson 2 auto-detection is planned to be switched off in 7.1 and its support removed in 7.2 ([7.0 notes](https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-7.0-Release-Notes)).

The platform inventory needs two corrections. A tree check shows **`XStreamMarshaller` and `PropertyPlaceholderConfigurer` both still exist in Spring 7.0.0** ([spring-framework v7.0.0](https://github.com/spring-projects/spring-framework/tree/v7.0.0)), so neither is a removal blocker. The 6.2 placeholder-parser rewrite applies to both, though, and XStream itself needs `--add-opens` on JDK 17+ and has no plans for module support ([XStream FAQ](https://raw.githubusercontent.com/x-stream/xstream/master/xstream-distribution/src/content/faq.html)). Versioned `spring-beans-3.1.xsd`-style references also keep resolving in 7.x, because `spring.schemas` aliases them to the current schema ([spring-beans spring.schemas](https://github.com/spring-projects/spring-framework/blob/main/spring-beans/src/main/resources/META-INF/spring.schemas)). Rewriting them (MOD-I15) is hygiene rather than a blocker. Spring Security's namespace is different. Its 7.0 handler fails fatally on any XSD older than `spring-security-7.0.xsd`, and XML `request-matcher` accepts only `path`, `regex` or `ciRegex` ([SecurityNamespaceHandler 7.0](https://github.com/spring-projects/spring-security/blob/7.0.x/config/src/main/java/org/springframework/security/config/SecurityNamespaceHandler.java), [spring-security-7.0.rnc](https://github.com/spring-projects/spring-security/blob/7.0.x/config/src/main/resources/org/springframework/security/config/spring-security-7.0.rnc)). The three `spring-security-4.2.xsd` files should switch to the unversioned schema in phase 1 (MOD-I29).

Security's behavioural changes matter more than its renames. Under 5.8's "prepare for 6.0" model, `SecurityContextHolderFilter` only reads the security context, so **authentication mechanisms must save the context explicitly**. uPortal's two custom `AbstractPreAuthenticatedProcessingFilter` subclasses (portal and Soffit) would otherwise force re-authentication on every request ([5.8 session-management migration](https://github.com/spring-projects/spring-security/blob/5.8.x/docs/modules/ROOT/pages/migration/servlet/session-management.adoc)). CSRF tokens become deferred and BREACH-masked, which changes what JavaScript clients have to send ([5.8 exploits migration](https://github.com/spring-projects/spring-security/blob/5.8.x/docs/modules/ROOT/pages/migration/servlet/exploits.adoc)). 7.0 moves the Access API into `spring-security-access` and makes login redirects relative ([Security 7.0 what's new](https://github.com/spring-projects/spring-security/blob/7.0.x/docs/modules/ROOT/pages/whats-new.adoc)). Each 5.8 toggle should be its own PR, flipped while still on javax. CAS is less disruptive than it looks. uPortal uses Jasig cas-client filters, not `spring-security-cas`, so what matters is the client's move to Apereo cas-client 4.x (`org.apereo.cas.client`, Jakarta). **cas-client 4.1.1 compiles for Java 21 and requires Servlet 6.1** ([cas-client 4.1.1 POM](https://repo1.maven.org/maven2/org/apereo/cas/client/cas-client/4.1.1/cas-client-4.1.1.pom)), so the Spring 6.2 checkpoint needs the 4.0 line, which is Jakarta on JDK 17 ([spring-security#11674](https://github.com/spring-projects/spring-security/issues/11674)). Passwords are mostly unaffected by Spring Security's `DelegatingPasswordEncoder` change because uPortal hashes with jasypt and its own code. jasypt has been unmaintained since 2019, though ([jasypt on Maven Central](https://repo1.maven.org/maven2/org/jasypt/jasypt/maven-metadata.xml)), so 6.0 should include a small in-tree verifier for the legacy MD5/SHA-256 formats and rehash to a modern algorithm on successful login, following the `upgradeEncoding` pattern Spring uses ([DaoAuthenticationProvider](https://raw.githubusercontent.com/spring-projects/spring-security/main/core/src/main/java/org/springframework/security/authentication/dao/DaoAuthenticationProvider.java)).

The companion projects are actively maintained, except for their portlet integration classes. Spring Web Flow 4.0.1 runs on Spring 7 and received two CVE fixes in June 2026, but **its portlet integration disappeared in 2.5** ([spring-webflow releases](https://github.com/spring-projects/spring-webflow/releases), [spring-webflow v2.5.0](https://github.com/spring-projects/spring-webflow/tree/v2.5.0.RELEASE)). Spring Session 2.0 split its modules, removed multi-user browser sessions and restructured the JDBC schema ([Spring Session 2.0 docs](https://github.com/spring-projects/spring-session/blob/2.0.0.RELEASE/docs/src/docs/asciidoc/index.adoc)). uPortal uses the Redis store, and serialized session attributes break at the jakarta hop anyway, so the honest plan is to drop sessions at upgrade (MOD-I32). springfox has been dead since 2020. springdoc v3 tracks Spring Boot 4 and describes itself as Boot-oriented ([springdoc README](https://github.com/springdoc/springdoc-openapi/blob/main/README.md)), so running it in a non-Boot WAR needs a wiring spike, with build-time OpenAPI generation as the fallback. json-lib-ext-spring (2008) and spring-modules-cache have no successors and should be replaced by Jackson views and Spring's own cache abstraction.

Jackson 3 hides a data trap. Spring's own announcement says Jackson 3 now **sorts properties alphabetically and writes dates as ISO-8601 strings by default** ([Introducing Jackson 3 support in Spring](https://spring.io/blog/2025/10/07/introducing-jackson-3-support-in-spring)). uPortal persists Jackson output in `JacksonType` and `StatisticsJacksonType` columns and serves it to web components over REST. So the persistence-side `JsonMapper` must be configured with Jackson 2 defaults, and golden-file tests must pin both the stored JSON and the REST payloads (MOD-I31). Spring Security's Jackson 3 modules read the Jackson 2 format ([Security 7.0 migration](https://github.com/spring-projects/spring-security/blob/7.0.x/docs/modules/ROOT/pages/migration/index.adoc)), which removes one worry.

### Caching needs a common cache API before it needs a provider

uPortal uses Ehcache 2 directly in 58 files, including `Element`, `SelfPopulatingCache` and the search API. It defines 184 regions, of which about 106 are Hibernate regions and four carry the 4.3 query-cache names that 5.3 renamed, and it uses 110 JGroups replicator factories ([persistence inventory](./codebase_inventory_persistence.md)). Spring 6.0 removed `EhCacheCacheManager`, and Hibernate's `hibernate-ehcache` never got past a 6.0 alpha ([hibernate-ehcache metadata](https://repo1.maven.org/maven2/org/hibernate/hibernate-ehcache/maven-metadata.xml)). The structural problem is clustering. **Ehcache 3 has no JGroups, RMI or JMS replication, and its clustering requires a Terracotta server** ([Ehcache 3 clustered cache docs](https://github.com/ehcache/ehcache3/blob/master/docs/src/docs/asciidoc/user/clustered-cache.adoc)). Infinispan embedded uses JGroups and defaults its Hibernate entity caches to synchronous invalidation. It publishes `infinispan-hibernate-cache-v66` for Hibernate 6.6 and 7.1+ ([Infinispan 2LC reference](https://raw.githubusercontent.com/infinispan/infinispan/main/documentation/src/main/asciidoc/topics/ref_hibernate_second_level_cache.adoc), [Infinispan v6.6 dependency](https://github.com/infinispan/infinispan/blob/main/documentation/src/main/asciidoc/topics/dependencies_maven/hibernate_v6.6.xml)). That makes it the closest functional replacement for adopters who run clusters.

The following sequencing facts sharpen MOD-I4. First, the JCache API keeps the `javax.cache` package because JSR-107 never moved to Jakarta ([cache-api metadata](https://repo1.maven.org/maven2/javax/cache/cache-api/maven-metadata.xml)). So the whole cache migration can finish before the namespace switch. Any blanket `javax.`→`jakarta.` text rewrite must exclude `javax.cache`, along with `javax.portlet`, `javax.xml`, `javax.naming` and `javax.sql`. Second, **Ehcache 3.12 is compiled for Java 17**, and 3.11 was the last line for Java 8 ([Ehcache 3 releases](https://github.com/ehcache/ehcache3/releases)), so the provider switch has to wait for the runtime JDK bump or use Caffeine (Java 11) in the meantime. NotificationPortlet already runs Ehcache 3.12 next to Spring 4.3, which shows the library combination works. Third, Hibernate's JCache integration creates unconfigured regions with a warning by default and may make them unbounded. Tests should set `missing_cache_strategy=fail`. The timestamps region must never expire ([Hibernate caching guide](https://raw.githubusercontent.com/hibernate/hibernate-orm/main/documentation/src/main/asciidoc/userguide/chapters/caching/Caching.adoc)). So the order is uPortal's cache calls routed through Spring Cache/JCache while still on Spring 4.3, then the provider (Ehcache 3 locally, with Infinispan as the clustered option), then Hibernate's second-level cache on `hibernate-jcache` at the 5.6 hop. The 5.3 SPI break forces that last step anyway, because it breaks `SpringBeanEhCacheRegionFactory`.

Joda-Time follows the same pattern. Joda itself is still maintained, but Spring 6 dropped its formatting integration, and Jadira blocks Hibernate 6. The 86 Joda files can move to `java.time` on Hibernate 5.2, where `java.time` support is native ([5.2 guide](https://github.com/hibernate/hibernate-orm/blob/5.2/migration-guide.adoc)). OpenRewrite's `NoJodaTime` can do the bulk rewrite locally, and the remaining semantic differences such as `withZone` need hand fixes ([OpenRewrite NoJodaTime](https://docs.openrewrite.org/recipes/java/joda/time/nojodatime)). Jadira's storage should be reproduced with `AttributeConverter`s, which are the most API-stable choice across 6.x, 7.x and 8.0. Correctness is proven by round-trips under DST-observing JVM time zones.

## uPortal has no Jakarta portlet container to adopt

The portlet layer is where uPortal differs most from CAS, and where the 6.0 plan carries real research risk. **Apache Portals retired in September 2025, its move to the Attic completed in November 2025, and `apache/portals-pluto` was archived on 29 October 2025**. Its last release, Pluto 3.1.2 from December 2023, is still javax ([apache/portals-pluto](https://github.com/apache/portals-pluto), <!-- vale ai-tells.ColonUsage = NO --><!-- citation link text kept verbatim -->[Attic: Apache Portals](https://attic.apache.org/projects/portals.html)<!-- vale ai-tells.ColonUsage = YES -->, [Pluto on Maven Central](https://repo1.maven.org/maven2/org/apache/portals/pluto/pluto-container/maven-metadata.xml)). The Jakarta Portlet 4.0 specification repository has no tags, and **`jakarta/portlet` returns 404 on Maven Central** ([jakartaee/portlet](https://github.com/jakartaee/portlet), [Maven Central jakarta/portlet](https://repo1.maven.org/maven2/jakarta/portlet/)). The only Jakarta container is Liferay's Plutonium 4.0, an Apache-2.0 fork of Pluto 3, which exists as a single-maintainer 4.0.0-M1 published to Liferay's own Nexus rather than Central ([liferay/plutonium](https://github.com/liferay/plutonium)). PortletMVC4Spring 6.0.0-M1 targets Spring 6.2.10 and Jakarta Portlet 4.0 through "non-official" Liferay coordinates and has no Spring 7 line ([portletmvc4spring 6.0.0-M1 POM](https://github.com/liferay/portletmvc4spring/blob/6.0.0-M1/pom.xml)). Liferay's own Jakarta transition required recompiling every portlet against Portlet 4.0 ([Liferay Jakarta FAQ](https://learn.liferay.com/w/reference/jakarta-2025-faq)). Adopting the Liferay stack (option A1) would mean porting uPortal's Pluto 2.1 SPI to Pluto 3 semantics and rebuilding every portlet, all on milestone artifacts that one engineer maintains.

Sakai, an Apereo sibling, faced the same choice and took a different route. Its PR #15141, merged on 9 October 2026, moved Sakai to Tomcat 10.1, Java 21, Spring 6 and Hibernate 6 by **importing Pluto 1.1.7 into its own source tree and compiling `javax.portlet` against `jakarta.servlet`**. Its vendored `PortletServlet` imports both namespaces, and later commits reverted a package rename back to `org.apache.pluto` ([Sakai PR #15141](https://github.com/sakaiproject/sakai/pull/15141), [Sakai PortletServlet](https://raw.githubusercontent.com/sakaiproject/sakai/master/libs/pluto/pluto-container/src/main/java/org/apache/pluto/core/PortletServlet.java)). uPortal's case is harder in one specific way. The Portlet 2.0 API exposes `javax.servlet.http.Cookie[] getCookies()` on `PortletRequest` ([PortletRequest.java](https://raw.githubusercontent.com/apache/portals-pluto/master/portlet-api/src/main/java/javax/portlet/PortletRequest.java)), so the hybrid API jar has to be rebuilt deliberately with `Cookie` taken from `jakarta.servlet`. Neither the Tomcat migration tool nor Eclipse Transformer renames `javax.portlet`. **No migration-tool profile includes it** ([EESpecProfiles.java](https://raw.githubusercontent.com/apache/tomcat-jakartaee-migration/main/src/main/java/org/apache/tomcat/jakartaee/EESpecProfiles.java), [Transformer jakarta-renames](https://raw.githubusercontent.com/eclipse-transformer/transformer/main/org.eclipse.transformer.jakarta/src/main/resources/org/eclipse/transformer/jakarta/jakarta-renames.properties)). That gap actually helps the hybrid design: a transformed portlet WAR ends up with exactly the mixed references that a hybrid API provides. The model Pluto relies on also survives. Tomcat 11 still supports `crossContext` and the `sessionCookiePath="/"` setting that portlet implementations use ([Tomcat 11 context docs](https://raw.githubusercontent.com/apache/tomcat/11.0.x/webapps/docs/config/context.xml)).

| Option | What it takes | Effort | Technical risk | Sustainability risk | Verdict for 6.0 |
|---|---|---|---|---|---|
| A1. Liferay Plutonium 4 + Jakarta Portlet 4.0 + PortletMVC4Spring (forked to Spring 7) | Port uPortal's Pluto 2.1 SPI to Pluto 3 and rebuild every portlet on Portlet 4.0 | XL | Medium to high | High (milestones, one maintainer, off Central) | Revisit if Jakarta Portlet 4.0 and Plutonium reach Central |
| A2. In-tree Pluto 2.1 on jakarta.servlet + hybrid javax.portlet 2.0 API | Vendor Pluto 2.1 container, driver and taglib sources, move uPortal's 67 Pluto-coupled files to jakarta.servlet, and rebuild the API jar | L | Medium (Sakai precedent; Cookie wrinkle) | Medium (uPortal maintains a non-standard API) | **Adopt** as the in-uPortal container |
| B. Keep portlets on a separate Tomcat 9 | Second portal host, iframe or proxy | M to L | Medium | High (EOL stack, two sessions) | Reject, because Pluto dispatch needs one container |
| C. Transform portlet WARs (build time or `legacyAppBase`) | Requires A2 underneath | M on top of A2 | High (removed Servlet 6 APIs surface at runtime) | High (EOL Spring 3.2/4.3 bytecode) | **Adopt, time-boxed, to keep the WARs running until they are replaced**, build-time only |
| D. Soffit / REST + custom elements | Native channel type, re-platform portlets | L overall | Low to medium | Low | **Strategic end state**, delivered in 6.x |

Can existing portlet WARs keep working on Jakarta? Not unmodified, and not with confidence on day one. They can work if three conditions hold together. uPortal puts the hybrid API in Tomcat's `shared/lib`, the in-tree Pluto runs on jakarta.servlet, and every WAR is transformed at build time with a rule set limited to what Tomcat provides (servlet, JSP, EL and websocket). That rule set leaves each WAR's private `javax.persistence` and `javax.mail` intact. The Tomcat 11 `legacyAppBase` directory can do this automatically on deploy, but only with default settings ([Tomcat 11 host docs](https://raw.githubusercontent.com/apache/tomcat/11.0.x/webapps/docs/config/host.xml)). The transformation should run in uPortal-start's overlay build instead, next to the `GradlePlutoPlugin` step that already rewrites each WAR's `web.xml`. That makes the artifacts deterministic and testable. The residual risk is concrete. Servlet 6.0 removed long-deprecated classes and methods ([Servlet spec changes](https://raw.githubusercontent.com/jakartaee/servlet/master/spec/src/main/asciidoc/servlet-spec-body.adoc)), and the transformed WARs contain Spring 3.2 (Feedback), Spring 4.3 and Hibernate 3.x bytecode that may call them on rarely exercised paths. A static bytecode scan for removed Servlet APIs plus the per-portlet Playwright specs are the defence. There is no public precedent for running unmodified JSR-286 WARs this way, so the Phase 5 spike decides whether transformed WARs actually run.

Should everything be ported to web components instead? For 6.0, no. Today's web components depend on the portlet stack themselves: `waffle-menu` and `notification-icon` are placed through SimpleContentPortlet "Advanced CMS" definitions ([waffle-menu definition](https://github.com/uPortal-Project/uPortal-start/blob/master/data/quickstart/portlet-definition/waffle-menu.portlet-definition.xml)). The Soffit connector is itself a Spring Portlet MVC portlet ([SoffitConnectorController](https://github.com/uPortal-Project/uPortal/blob/master/uPortal-soffit/uPortal-soffit-connector/src/main/java/org/apereo/portal/soffit/connector/SoffitConnectorController.java)). The component repositories are Vue 2, which reached end of life at the end of 2023, and have been dormant since early 2024 ([Vue 2 EOL](https://v2.vuejs.org/eol/), [uPortal-web-components](https://github.com/uPortal-Project/uPortal-web-components)). The bundled portlets add up to roughly 60k lines of mostly server-side Java (CalDAV, RSS, proxying, LTI/OAuth, persistence) across the [uPortal-Project portlet repositories](https://github.com/orgs/uPortal-Project/repositories), so "porting" one means splitting it into a Jakarta REST service plus a custom element, which is the pattern NotificationPortlet and esup-filemanager already follow. Upstream portlet maintainers also spent April to September 2026 pinning those repositories to Java 11 and blocking Jakarta and Spring 5+ updates in Renovate ([WebproxyPortlet PR #278](https://github.com/uPortal-Project/WebproxyPortlet/pull/278), [CalendarPortlet PR #370](https://github.com/uPortal-Project/CalendarPortlet/pull/370)). The build-time transformation of those WARs lets 6.0 be released without changing those repositories. In 6.x, the order is: first a native web-component channel type in the rendering pipeline and the Soffit connector as a pipeline component, which are first moves #2, #3 and #7 of the maintainers' subsystem analysis ([subsystem-analysis.md](https://github.com/uPortal-Project/uPortal/blob/master/docs/architecture/subsystem-analysis.md)). After that come the ports, cheapest and most valuable first. Calendar's narrow view already became a vanilla `<calendar-portlet>` element that keeps its Playwright selectors ([CalendarPortlet PR #409](https://github.com/uPortal-Project/CalendarPortlet/pull/409)). cas-proxy-test, dormant since 2018, should simply be retired.

The same reasoning settles the in-uPortal portlet framework. **PortletMVC4Spring's 5.x README says it requires Portlet 3.0, yet uPortal's portlet parent pins `portletmvc4spring` 5.2.0 as "last Portlet 2.0 compatible"**, and SimpleContentPortlet runs it on uPortal-start's Pluto 2.1 today ([SimpleContentPortlet PR #550](https://github.com/uPortal-Project/SimpleContentPortlet/pull/550), [uportal-portlet-parent POM](https://github.com/uPortal-Project/uportal-portlet-parent/blob/main/pom.xml)). The practical plan is to vendor Spring 4.3.30's `web.portlet` package and Web Flow 2.4.8's 42 portlet files into an `org.apereo.portal` package while still on Spring 4.3. That vendoring is a pure refactor, and the build remains green. PortletMVC4Spring 5.2.0's diffs then serve as the map for the Spring 5 adaptations. This splits WORKSTREAMS' second "atomic" step (Spring 5 together with the Portlet MVC replacement) into a safe pre-step and a much smaller bump.

## Tomcat 11 remains the runtime; Boot and Jetty are optional

MOD-Q1 resolves in favour of keeping the external Tomcat. Tomcat 11 is a Servlet 6.1 container that still supports cross-context dispatch. Both Spring Boot 4 and CAS 8 build on it, and it can convert javax WARs in `webapps-javaee` ([Tomcat 11 context docs](https://raw.githubusercontent.com/apache/tomcat/11.0.x/webapps/docs/config/context.xml), [Spring Boot 4.0 release notes](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Release-Notes)). Spring Boot 4 can wrap an XML-configured WAR with `SpringBootServletInitializer` and `@ImportResource`. JSPs work only with WAR packaging, though, and **Boot documents no way to host additional WAR contexts in embedded Tomcat** ([Boot traditional deployment](https://raw.githubusercontent.com/spring-projects/spring-boot/main/documentation/spring-boot-docs/src/docs/antora/modules/how-to/pages/deployment/traditional-deployment.adoc), [Boot servlet reference](https://raw.githubusercontent.com/spring-projects/spring-boot/main/documentation/spring-boot-docs/src/docs/antora/modules/reference/pages/web/servlet.adoc)). An embedded uPortal could not host the portlet WARs that the Playwright specs exercise. Boot's useful contributions are its dependency BOM, imported as a Gradle `platform()` so versions stay aligned with the CAS 8 combination, and Actuator later in 6.x. Jetty 12.1 is the one container that can run ee8 (javax) and ee11 (jakarta) webapps side by side with cross-environment dispatch, and its test plans cover ee11→ee8 forwards ([Jetty cross-context test plans](https://github.com/jetty/jetty.project/tree/jetty-12.1.x/tests/test-cross-context-dispatch/ccd-tests/src/test/resources/plans)). However, an ee10/ee11 bug that ran dispatched servlets with the *source* context's identity and classloader was fixed only on 30 September 2026 ([Jetty PR #15763](https://github.com/jetty/jetty.project/pull/15763)), cross-context dispatch bypasses the security handler ([Jetty PR #11451](https://github.com/jetty/jetty.project/pull/11451)), and Pluto passes container objects across the boundary that would need javax↔jakarta adapters. Jetty 12.1 is a spike candidate, not the 6.0 runtime.

The Tomcat ladder has its own gotchas, which the uPortal-start config rebase must handle. Tomcat 9.0.74+ lowered `maxParameterCount` from 10,000 to 1,000, which can affect large admin forms such as the permissions grid, and the AJP connector now refuses to start without a secret ([Tomcat 9 migration](https://raw.githubusercontent.com/apache/tomcat-site/trunk/xdocs/migration-9.xml)). Tomcat 10.1 keeps only RFC 6265 cookies and drops APR ([Tomcat 10.1 migration](https://raw.githubusercontent.com/apache/tomcat-site/trunk/xdocs/migration-10.1.xml)). Tomcat 11 removes SecurityManager support and HTTP/2 push, keeps quotes on quoted cookie values, and can throw from `getParameter()` on parse errors ([Tomcat 11 migration](https://raw.githubusercontent.com/apache/tomcat-site/trunk/xdocs/migration-11.0.xml)). Its connectors default to **`maxPartCount` 50** ([Tomcat 11 HTTP connector docs](https://raw.githubusercontent.com/apache/tomcat/11.0.x/webapps/docs/config/http.xml)). Because `shared/lib` holds the Pluto and portlet API jars, a mixed javax/jakarta shared classloader cannot work. So Tomcat, `shared/lib`, uPortal and every portlet WAR have to flip in the same step.

The Java ladder sets the pace for the runtime. JDK 17 makes illegal reflective access fatal (JEP 403), and Gradle no longer adds implicit `--add-opens` to test workers ([JEP 403](https://openjdk.org/jeps/403), [Gradle 7 upgrade guide](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/releases/upgrading/upgrading_version_7.adoc)). JDK 20's CLDR data inserts U+202F before AM/PM, which breaks string-equality date assertions and JSTL `fmt` output checks ([Spring wiki: JDK 20 date formatting](https://github.com/spring-projects/spring-framework/wiki/Date-and-Time-Formatting-with-JDK-20-and-higher)). JDK 23 stopped discovering annotation processors implicitly ([JDK 23 release notes](https://www.oracle.com/java/technologies/javase/23-relnote-issues.html)). uPortal already declares its processors explicitly, so that one is harmless. JDK 24 permanently disabled the Security Manager ([JEP 486](https://openjdk.org/jeps/486)). uPortal-start's `setenv.bat` still probes for CMS flags, and CMS was removed in JDK 14, so a JVM given those flags refuses to start ([JEP 363](https://openjdk.org/jeps/363)). There is a subtler consequence for MOD-D3. Spring 5.3 is supported only up to JDK 21, so **the portal runtime should go 11 → 21 at the Spring 5.3 step and 25 only at the Spring 6.2 checkpoint**. JDK 25 test legs before that are informational. Hibernate 6.6 has supported Java 25 since 6.6.40 ([Hibernate 6.6 series data](https://github.com/hibernate/hibernate.org/blob/production/_data/projects/orm/releases/6.6/series.yml)).

For MOD-Q3 (local SSO), CAS 3.6 on Spring 3.2 is a blocker to remove rather than something to upgrade. Current CAS is Jakarta-only, and the 8.0 overlay targets Spring Boot 4.1 on Java 25 ([CAS overlay 8.0](https://raw.githubusercontent.com/apereo/cas-overlay-template/8.0/gradle.properties)). Apereo publishes `apereo/cas:v[A.B.C]` images "meant to be used as quickstarters and demos" ([cas-webapp-docker](https://github.com/apereo/cas-webapp-docker)). Whether an 8.0.x tag is published still needs checking. Generating a CAS Initializr overlay is the fallback. Keycloak speaks CAS only through a third-party extension that lacks proxy tickets ([keycloak-protocol-cas](https://github.com/jacekkow/keycloak-protocol-cas)). uPortal-start already enables `SimpleSecurityContextFactory` local login. So local login should become the default, with CAS 8 as an opt-in Compose service that also runs in CI so the Playwright `auth` spec keeps exercising CAS. The CAS 3.6 client can talk to a CAS 8 server over the CAS protocol (a general CAS compatibility fact, not re-verified here). So the server swap can be merged in phase 1. It has to be merged before uPortal-start's runtime JDK moves past 11, because CAS 3.6 would not run after that move.

## Gradle 9 is forced; Kotlin DSL is optional

Both repositories use APIs that Gradle removed. `compile`, `runtime` and `testCompile`, the legacy `maven` plugin and `uploadArchives` went in 7.0. `archiveName` and `classifier` went in 8.0. **The Convention API went in 9.0**, and uPortal-start's vendored `WarOverlayPlugin` calls `project.convention.plugins.warOverlay` ([Gradle 6→7](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/releases/upgrading/upgrading_version_6.adoc), [Gradle 7→8](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/releases/upgrading/upgrading_version_7.adoc), [Gradle 9 major upgrade](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/releases/upgrading/upgrading_major_version_9.adoc)). Gradle 9 also fails a `test` task whose test sources contain no discovered tests. It puts Groovy 4 semantics into build scripts and needs an explicit `junit-platform-launcher`. The 9.x line deprecates map dependency notation, implicit parent-project property lookup and configuration-time process execution ahead of Gradle 10 ([Gradle 9.x upgrade guide](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/releases/upgrading/upgrading_version_9.adoc)). The safe path is three hops, 7.6.x, 8.14.x and then 9.8.x, each with `--warning-mode all` clean. OpenRewrite's `MigrateToGradle9` helps on the last hop, but the buildSrc plugins need hand edits ([OpenRewrite MigrateToGradle9](https://docs.openrewrite.org/recipes/gradle/migratetogradle9)).

The surrounding tools move along with Gradle. google-java-format now needs **JDK 21 to run** ([google-java-format README](https://raw.githubusercontent.com/google/google-java-format/master/README.md)). The unmaintained sherter plugin (last release 2020) should give way to Spotless 8.x, which needs Java 17 and Gradle 8.1+ and keeps AOSP style through `googleJavaFormat().aosp()` ([Spotless README](https://raw.githubusercontent.com/diffplug/spotless/main/plugin-gradle/README.md)). That is the owner's PR #2988. Error Prone 2.43+ also needs JDK 21 ([Error Prone installation](https://errorprone.info/docs/installation)). Groovy 3 has no JDK 25 support statement, so tests move to Groovy 4 or 5, Spock 2.4/2.5 (which states it is tested on Java 25) and CodeNarc 4.0 ([Spock release notes](https://raw.githubusercontent.com/spockframework/spock/master/docs/release_notes.adoc), [Groovy 5 release notes](https://raw.githubusercontent.com/apache/groovy-website/asf-site/site/src/site/releasenotes/groovy-5.0.adoc), [CodeNarc changelog](https://raw.githubusercontent.com/CodeNarc/CodeNarc/master/CHANGELOG.md)). Mockito 5 needs its agent passed as `-javaagent` on JDK 21+ ([Mockito javadoc](https://raw.githubusercontent.com/mockito/mockito/main/mockito-core/src/main/java/org/mockito/Mockito.java)), and JaCoCo 0.8.14 is the first release with official Java 25 support ([JaCoCo changes](https://raw.githubusercontent.com/jacoco/jacoco/master/org.jacoco.doc/docroot/doc/changes.html)). OSSRH reached end of life on 30 June 2025. Publishing should move to `maven-publish` plus a Central Portal publisher, either `gradle-nexus` publish-plugin 2.0 against the staging API URLs uPortal already uses, or vanniktech 0.37 ([gradle-nexus README](https://raw.githubusercontent.com/gradle-nexus/publish-plugin/master/README.md), [vanniktech Central docs](https://raw.githubusercontent.com/vanniktech/gradle-maven-publish-plugin/main/docs/central.md)). The CI matrices still use `adopt-hotspot`, which `actions/setup-java` v6 removed ([setup-java README](https://raw.githubusercontent.com/actions/setup-java/main/README.md)). That is MOD-I33, a one-line fix that can land today. Playwright 1.58.2 → 1.64.0 is low risk. The changes to watch are that 1.64 forwards `screen` from device descriptors and that Ubuntu 20.04 runners are no longer supported ([Playwright release notes](https://raw.githubusercontent.com/microsoft/playwright/main/docs/src/release-notes-js.md)).

For MOD-Q2, Gradle's own guidance sets the order. It recommends version catalogs, convention plugins in a `build-logic` included build rather than `buildSrc`, and Kotlin DSL for *new* builds, while Groovy DSL is not deprecated ([Gradle best practices: dependencies](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/best-practices/best_practices_dependencies.adoc), [structuring builds](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/best-practices/best_practices_structuring_builds.adoc), [general](https://raw.githubusercontent.com/gradle/gradle/master/platforms/documentation/docs/src/docs/userguide/best-practices/best_practices_general.adoc)). Renovate reads both `gradle.properties` and TOML catalogs ([Renovate Java docs](https://git.shivering-isles.com/github-mirror/renovatebot/renovate/-/blob/8af89d27d01982dbe72297b601ad4f618f57d5eb/docs/usage/java.md)). Kotlin DSL would bring typed accessors and IDE navigation, but it unblocks nothing on the 6.0 critical path. Every converted script also costs review time from a project whose Gradle 8.5 PR has waited eight months for one ([uPortal PR #2921](https://github.com/uPortal-Project/uPortal/pull/2921)). The Gradle 9 removals force the uPortal-start buildSrc plugins to be rewritten anyway, so they should be rewritten as typed Java or Kotlin plugins in `build-logic`. Script-level Kotlin DSL conversion waits until after 6.0. The upstream proposal should also confront the published roadmap's "Maven" and "Replace Gradle (2028)" items so that build work is not rejected later on direction ([roadmap.md](https://github.com/uPortal-Project/uportal-project.github.io/blob/master/roadmap.md)). [ADR 0003](../../adr/0003-build-with-gradle-9-before-raising-the-bytecode-level.md) now does that.

The operating rules for sub-agents extend those already in WORKSTREAMS.md. Each agent works on one workstream in one git worktree. It publishes snapshots to its own `-Dmaven.repo.local`, and after WS2 is merged it runs its portal on its own port offset, so Playwright no longer serializes the whole team. Each agent produces one Conventional Commit per intended upstream PR, with a commit body in "Problem / Goal / Changes" form that cites its `MOD-` IDs. It touches version lines in `gradle.properties` only in a dedicated commit, and it records every decision as a new `MOD-D` entry with the alternatives considered. Only the integrator merges into the `ccr-*` branch, and it does so only after all required checks pass: uPortal `build`, uPortal-start `portalInit`, every Playwright spec and the DB harness. The spike agent never merges. Its job is to make sure the plan's assumptions are disproved early rather than late.

## Upstream through ADRs and a milestone train

The upstream plan has to work with how the project actually operates. uPortal is still on Java 11 and Spring 4.3, and it raised Hibernate only to 4.3 in August 2026 ([PR #3012](https://github.com/uPortal-Project/uPortal/pull/3012)). Renovate explicitly blocks Spring 5+, Spring Security 5+ and Hibernate majors because "each major is a coordinated migration we are not ready for" ([PR #2948](https://github.com/uPortal-Project/uPortal/pull/2948)). The April 2025 uP6 thread pulled Tomcat back from 11 to 9 so that the project would not "have to worry about the change from 'javax' to 'jakarta' packages" ([uportal-user thread](https://groups.google.com/a/apereo.org/g/uportal-user/c/d9ktfsL_f6E)). The published roadmap gives uP6 Java 21 and converting external portlets, and gives uP7 dropping portlets ([roadmap.md](https://github.com/uPortal-Project/uportal-project.github.io/blob/master/roadmap.md)). Since October 2025, one maintainer has performed 43 of 45 merges ([uPortal commits](https://github.com/uPortal-Project/uPortal/commits/master)). So a Jakarta 6.0 needs explicit consent before it needs code. This report proposed an RFC in `uPortal-Project/community` Discussions, which the project created in July 2026 precisely for "design proposals / RFCs" and cross-repo epics ([community README](https://github.com/uPortal-Project/community)), announced on uportal-dev as CONTRIBUTING asks ([CONTRIBUTING.md](https://github.com/uPortal-Project/uPortal/blob/master/docs/CONTRIBUTING.md)). MOD-D36 replaced the RFC with one ADR per decision, each going upstream with the pull request for its code ([ADR index](../../adr/README.md)).

The RFC was to do five things. The ADRs now cover the first two and most of the third. No ADR covers the session flush, the Lucene reindex, the branch model, review capacity or authorship yet. It should state that 6.0 is uP6 and uP7 combined, with Java 25 rather than 17 or 21 and Tomcat 11 rather than 9 ([ADR 0002](../../adr/0002-target-java-25-and-jakarta-ee-11-in-steps.md), [ADR 0004](../../adr/0004-deploy-uportal-as-a-war-on-an-external-tomcat-11.md)). The build stays on Gradle rather than moving to Maven ([ADR 0003](../../adr/0003-build-with-gradle-9-before-raising-the-bytecode-level.md)). It should present the portlet strategy above as a plan that keeps portlets supported through 6.x while moving toward web components, and make clear that portlets are not being dropped ([ADR 0011](../../adr/0011-keep-portlet-mvc-and-pluto-in-uportal-and-transform-portlet-wars.md), [ADR 0012](../../adr/0012-replace-built-in-portlets-before-the-jakarta-switch.md)). It should list the adopter prerequisites: 5.17.x first, the minimum database versions ([ADR 0009](../../adr/0009-run-on-current-database-servers-with-a-measured-index-set.md)), Java 25, Tomcat 11, a session flush, a Lucene reindex, and the PostgreSQL LOB caution ([ADR 0008](../../adr/0008-move-to-an-improved-6-0-schema-with-a-copy-tool.md)). It should propose the branch model: `master` becomes 6.0 development once accepted, `rel-5-17-patches` gets 5.x fixes for a stated period, uPortal-start gets a `6.x` branch because adopters fork `master` and the repository has no tags ([uPortal-start README](https://github.com/uPortal-Project/uPortal-start)), and Renovate pins are lifted phase by phase. Finally, it should address review capacity directly, by asking for a second reviewer per phase and committing the author to co-maintain the vendored portlet framework and Pluto fork. The ICLA requirement applies to every human contributor ([CONTRIBUTING.md](https://github.com/uPortal-Project/uPortal/blob/master/docs/CONTRIBUTING.md)). Since sub-agents produce much of the prototype, the proposal should also disclose AI-assisted authorship. Commits have the human as author plus a `Co-Authored-By` trailer, and the proposal should confirm that the steering committee accepts this under the owner's ICLA.

PR slicing follows the phase table. Each PR maps to one GitHub issue and has a Conventional Commits title (`build!:` or `feat!:` for breaking ones) with `Refs MOD-…` and `Refs GH-…` footers. It uses the "Problem / Goal / Changes" body the maintainers already use. Each fills in the PR template's checklist, including `CHANGES.md` entries for any configuration or DDL impact ([PR template](https://github.com/uPortal-Project/uPortal/blob/master/.github/PULL_REQUEST_TEMPLATE.md)), and appends a fragment to a growing `docs/UPGRADING-6.0.md`. The owner's open PRs fit at the front of the queue. **#2988 (Spotless) should be merged first, nearly as is**. The gjf version bump should be split out as a format-only follow-up. **#2921 (Gradle 6.9.4 → 8.5)** has sat unreviewed since February 2026 ([PR #2921](https://github.com/uPortal-Project/uPortal/pull/2921)). It should be retargeted to the 7.6 hop and keep its decisions (Ant XJC, `maven-publish`, plugin versions), with the 8.14 and 9.8 hops following as separate PRs. That gives reviewers smaller diffs without discarding reviewed work. **uPortal-start #681** follows the same split and includes the build-logic rewrite. Release mechanics change with P1-2. Tags `6.0.0-M1` (after P4), `-M2` (after P7-1) and `-RC*` follow the train CAS used from 7.0 RC1 to GA ([CAS 7.0 RC3 notes](https://github.com/apereo/cas/blob/7.0.x/docs/cas-server-documentation/release_notes/RC3.md)), each smoke-tested through uPortal-start as `RELEASE.md` prescribes ([RELEASE.md](https://github.com/uPortal-Project/uPortal/blob/master/docs/developer/other/RELEASE.md)). The Central Portal publishing path is proven by a SNAPSHOT publish before the first milestone is cut.

## Conclusion

The Jakarta question for uPortal turns out to be mostly about compatibility. Spring and Hibernate follow published, cumulative migration guides, and CAS 8 shows the target combination works in Apereo's own ecosystem. The decisions that matter are about what uPortal must preserve that no upstream preserves for it. They cover a portlet container that nobody provides for Jakarta, ID-generation and LOB semantics that Hibernate's new dialects silently change, and a test baseline that has to be green before it can serve as a required check. Treating "zero DDL drift" and "every Playwright spec green on transformed WARs" as artifacts the plan produces, rather than outcomes it hopes for, is what makes the full-Jakarta ceiling achievable without a javax stopping point.

That approach also changes how the project is structured. Once the vendored Portlet MVC, the in-tree Pluto, the move to the JCache API and the Joda removal are merged on javax, the 6.0 release is mostly the scripted P6 switch and the P7 bump. What follows, the native web-component channel and portlet-by-portlet re-platforming, becomes ordinary 6.x feature work instead of a precondition. The timeline depends most on upstream consensus. For that reason the ADRs ([ADR index](../../adr/README.md)), the reuse of #2921 and #2988, and a second reviewer matter as much as any code change.
